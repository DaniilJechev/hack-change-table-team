## Зафиксированные решения
- Go: `net/http`, `pgx`, `goose`, официальный MCP Go SDK; один процесс с REST `/api/*`, MCP `/mcp`, редиректами `/r/*`.
- Слои: HTTP/MCP → прикладная логика → PostgreSQL. Для Этапа 0 внешние Go-зависимости не нужны.
- Локальный Docker Compose: PostgreSQL 16 + pgvector, Redis 7, Grafana, backend и agent.
- Аккаунты внешних сервисов ещё готовятся. Их отсутствие не блокирует каркас или будущий демо-режим.
- В полном демо backend и buddy-mcp настоящие, синтетические данные в БД; внешние MCP заменяются фикстурами. Уточнение OpenSpec согласовать с командой перед реализацией демо.
- Права: `X-Buddy-Key` для сервиса, `X-Buddy-User` для пользовательских операций; команда и роль берутся из БД.
- Только чтение корпоративных сервисов. Запись наших данных — через REST. Секреты только в локальном `.env`.
- Время в БД — UTC; повторные события и команды обрабатываются идемпотентно.

## Дальнейшие этапы дорожной карты

### Этап 1: готовые MCP и вход
- Закрепить с Эмилем OpenAPI, схемы MCP и данных, Docker entrypoint, события и формат журнала.
- Миграции, пользователи, команды, наставники, одноразовые приглашения; транзакционная привязка Telegram ID по коду и определение внутреннего пользователя.
- Идемпотентный загрузчик seed; Даниил поставляет синтетические данные по согласованным схемам.
- Jira и Calendar в отдельных Compose-сервисах. GitHub MCP — готовый бинарник внутри образа agent, stdio и read-only. Miro — удалённый сервер, OAuth/клиент у Эмиля.
- Зафиксировать совместимые версии; проверить настоящий `tools/list`, server-side ограничения и клиентские allowlists. Не включать внешние MCP в обязательные зависимости демо.

### Этап 2: buddy-mcp и REST
- Шесть инструментов чтения: `user_profile_get`, `team_card_get`, `team_faq_search`, `access_catalog_get`, `access_marks_get`, `interns_list`.
- Проверка пользователя на каждом вызове. Стажёр видит свою команду; наставник — своих стажёров; тимлид — свою команду.
- REST для брифов, событий, снимков календаря/доступов, вопросов, ответов, FAQ, отметок «я запросил», журнала MCP и статистики.
- Служебные интерфейсы для планировщика, источников по ID, настроек и feature flags.
- Ошибки с машинным кодом и русским сообщением; ошибки YAML с путями полей.

### Этап 3: хранение H1/H2
- Версии YAML-карточек; невалидная карточка не создаёт версию. FAQ: поиск PostgreSQL без LLM, публикация только с согласия автора.
- Хранить вопросы, эскалации, ответы и оценки; доставку сообщений делает агент.
- Повторное «я запросил» не сбрасывает первоначальную дату; ошибку проверки хранить отдельно от статуса доступа.
- Сводка наставника: X из 5 и зависшие объекты. Управление flags с проверкой роли.
- Источники карточек и FAQ — стабильные ID версии/раздела; Telegram deep links открывает агент после проверки пользователя.

### Этап 4: хранение H0/H3 и метрики
- Брифы, пункты, статусы отправки, снимки календаря, события кликов/прочтения и настройки.
- База сравнения календаря связана с последним успешно отправленным брифом; неудачная отправка и ошибка источника не уничтожают предыдущую базу.
- `/r/<item_id>`: непредсказуемый уникальный ID пункта, URL только из БД, без произвольного адреса в запросе. Первый сигнал устанавливает `read_at`, повторы не увеличивают число прочитанных брифов.
- `PUBLIC_BASE_URL` должен быть доступен устройству пользователя; серверный деплой и HTTPS отдельно не запрошены.
- pgvector и таблица чанков для RAG; размерность/модель закрепить с Эмилем до миграции. Индексация и поиск — его зона.
- Grafana: прочитанные брифы, брифы с переходом, «помогло» H2/H3, время до доступа, MCP-вызовы. Учётная запись Grafana только для чтения.

### Этап 5: надёжность и приёмка
- Тестировать авторизацию, повторное погашение приглашения, гонки и изоляцию команд; каждый относящийся к backend Scenario имеет тест.
- Проверять каждый MCP-инструмент настоящим SDK-клиентом; не публиковать инструменты записи.
- Проверять ошибки YAML, версии, согласие на FAQ, даты доступа, неудачные отправки, снимки, повторы событий и редиректы.
- Проверять агрегаты на известных данных и пустых выборках. Отклонённые попытки записи отличать от выполненных вызовов.
- Go race detector, vet, интеграционные тесты PostgreSQL, покрытие >80 %, OpenSpec, сборка образов.
- Чистый запуск, повторный seed, сохранность данных при перезапуске, сбои БД/MCP/Telegram, демо без внешних MCP-ключей и без LLM.
- PostgreSQL — источник истины; Redis — блокировки/лимиты, которые реализует агент.

### Этап 6: релиз
- Проверенная ветка и PR; слияние после проверки общей сборки.
- Тег релиза, проверка инструкции запуска для жюри, технические слайды про архитектуру и безопасность; доступ жюри — только по отдельному поручению.
