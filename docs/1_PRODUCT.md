## 3. H0 — утренний обход и бриф

### 3.1. Что делает и зачем
Каждое утро стажёр получает одно сообщение: что изменилось в его расписании, в Git и в Jira, и одно главное действие на день. Без брифа стажёр обходит несколько систем, пропускает комментарии к PR и переносы встреч, а наставник переспрашивает «ты видел мой коммент?». Бриф даёт ежедневную причину открывать бота.

### 3.2. Источники (ровно 3)

| Источник | Что отслеживаем (изменения с прошлого брифа) | Класс приоритета | Ссылка |
|---|---|---|---|
| **Google Calendar** | новая встреча или приглашение; приглашение без ответа; **перенос** («было → стало»); отмена; сменилась ссылка на созвон; встречи сегодня (со связанной задачей, если она есть в названии или описании) | Перенос или отмена сегодня → блокер; приглашение → запрос людей; встречи сегодня → информация | URL события в Google Calendar |
| **Git** (в прототипе — GitHub) | в PR стажёра **запросили изменения**; новые комментарии и ревью; PR одобрен или смёржен; **упала CI-проверка**; стажёра назначили ревьюером | Запрошены изменения, проверка упала → блокер; комментарии, ревью → запрос людей; апрув, мёрж → информация | URL PR / комментария |
| **Jira** | **назначена** задача; смена статуса; комментарий или **упоминание**; изменился дедлайн или приоритет; задачу переназначили | Упоминание → запрос людей; дедлайн ≤ 2 дней → дедлайн; новая задача → запрос людей; статус → информация | URL задачи / комментария |

### 3.3. Требования
| ID | Требование | Приоритет |
|---|---|---|
| FR-H0-01 | Сбор изменений из трёх источников с `since` = время последнего успешно отправленного брифа. Для Google Calendar (у MCP нет фильтра «изменено после») изменения находятся сравнением с сохранённым снимком событий | MUST |
| FR-H0-02 | Нормализация в `BriefItem {id, source, type, title, url, priority_class, related_task, before, after, created_at}` | MUST |
| FR-H0-03 | Ранжирование: блокеры → запросы людей → дедлайны → информация; не больше 5 пунктов; остаток — «Ещё N» | MUST |
| FR-H0-04 | Главное действие выбирает правило (первый пункт, требующий действия); LLM только формулирует | MUST |
| **FR-H0-LINK-1** | **Каждый пункт содержит ссылку на конкретный объект** (событие, PR или комментарий, задачу или комментарий) | MUST |
| **FR-H0-LINK-2** | Ссылка ведёт на объект, а не на главную страницу сервиса | MUST |
| **FR-H0-LINK-3** | Пункт без валидной ссылки не отображается; проверяет код, не LLM | MUST |
| **FR-H0-LINK-4** | LLM не создаёт и не меняет ссылки: код подставляет `url` по `item_id` | MUST |
| FR-H0-05 | Недоступный источник → бриф без блока + пометка | MUST |
| FR-H0-06 | Расписание: за 30 минут до первого стендапа в календаре, иначе 09:30; в выходные и дни отсутствия — нет | MUST |
| FR-H0-07 | `/brief` и «что нового?» — бриф немедленно | MUST |
| FR-H0-08 | Каждый бриф фиксирует статус «прочитан / не прочитан» и взаимодействия; `/stats` показывает метрики | MUST |
| FR-H0-09 | `/settings`: время брифа, тихий режим | SHOULD |

### 3.4. Пример
```

🟡 Jira: дедлайн ORD-101 — завтра                              [Открыть]
🟢 Git: PR #40 смёржен                                         [Открыть]
▶ Главное сегодня: синк перенесён на 12:00 — до него ответь на комментарии в PR #45
[✅ Прочитал]   Бриф полезен?  👍  👎
```

### 3.5. Метрики
| | Метрика | Цель |
|---|---|---|
| **Главная** | **Доля прочитанных брифов** — бриф считается прочитанным при любом сигнале от стажёра: [✅ Прочитал], переход по ссылке (через наш редирект), 👍/👎, ответ в чат | **≥ 60 %** |
| Поддерживающая | Доля брифов с действием (переход хотя бы по одной ссылке) | ≥ 40 % |
| Поддерживающая | 👍 среди оценённых | ≥ 70 % |
| Поддерживающая | Время реакции на «запросили изменения» (до и после бота) | ↓ в 2 раза |
| Защитная | Пунктов без ссылки | 0 |
| Защитная | Отписок от брифа | ≤ 10 % |

> Telegram Bot API не отдаёт ботам статус «прочитано», поэтому «прочитан» = первый сигнал от стажёра после отправки: кнопка, переход по ссылке, реакция или ответ. Переходы считаем через редирект `/r/<item_id>` в нашем бэкенде.

## 4. H1 — мониторинг доступов (только чтение)

### 4.1. Что делает и зачем
Чек-лист Авито поручает наставнику: «Проверь, запросил ли стажёр доступы ко всем необходимым программам…» (строка 2). Агент берёт эту проверку на себя:
- показывает, к каким из 5 инструментов доступ есть, а к каким нет;
- объясняет, **где и как запросить** недостающее;
- запоминает, что стажёр запросил доступ, и проверяет, когда он **реально появился**;
- если доступ не появился за 48 часов — готовит стажёру черновик напоминания владельцу;
- наставник видит сводку одной командой.

**Агент не создаёт заявок и ничего не меняет** — ни прав, ни досок, ни чатов.

### 4.2. Пул (ровно 5 инструментов)

| # | Инструмент | Объект | Как агент проверяет доступ (только чтение) | Где запросить (ответ стажёру) |
|---|---|---|---|---|
| 1 | **Git (GitHub)** | Репозиторий команды | Есть ли стажёр среди участников репозитория (`list_repository_collaborators`) или в команде (`get_team_members`) | Ссылка и владелец из каталога |
| 2 | **Jira** | Проект команды | Есть ли стажёр среди тех, кому можно назначать задачи в проекте (`jira_search_assignable_users`) | То же |
| 3 | **Miro** | Доска команды | Есть ли стажёр среди участников доски (`content_item_list_roles`, официальный Miro MCP) | То же |
| 4 | **Google Calendar** | Командные встречи (стендап, планирование, демо) | Есть ли стажёр среди участников регулярных встреч команды (`list-events` в календаре команды) | «Попроси наставника добавить тебя в встречи» |
| 5 | **Telegram** | Чат команды + канал Tech-dep | `getChatMember` — реальный Telegram API (бот — администратор чата) | «Попроси наставника добавить в чат» + имя администратора |

### 4.3. Статусы и ответы агента
| Статус | Когда | Что говорит агент |
|---|---|---|
| `granted` | Проверка в инструменте прошла | «Доступ к Miro есть ✅ [Открыть доску]» |
| `missing` | Доступа нет, стажёр ещё не запрашивал | «Доступа к Miro нет. Запросить: [Где запросить] — владелец Олег. Когда запросишь — нажми [Я запросил]» |
| `requested` | Стажёр нажал [Я запросил], доступа пока нет | «Ждём доступ к Miro (1 день). Проверяю каждый час» |
| `stale` | `requested` дольше 48 ч | «Доступа к Miro нет уже 3 дня. Вот черновик напоминания Олегу [Скопировать]». Отправляет сам стажёр |
| `forbidden` | Объект закрыт для роли стажёра | «prod-репозиторий стажёрам не выдаётся. Если нужен — обсуди с наставником» |

### 4.4. Требования
| ID | Требование | Приоритет |
|---|---|---|
| FR-H1-01 | Пакет роли «Backend-стажёр» = 5 инструментов с конкретными объектами из каталога | MUST |
| FR-H1-02 | Статус по каждому: `granted / missing / requested / stale / forbidden` | MUST |
| FR-H1-03 | Проверка доступа — **в самом инструменте** через MCP или Telegram API | MUST |
| FR-H1-04 | Для `missing` — где запросить и у кого (из каталога) + кнопка [Я запросил] | MUST |
| FR-H1-05 | Анализ задачи Jira: какие объекты из 5 инструментов упомянуты и каких не хватает | MUST |
| FR-H1-06 | Неоднозначность → уточнение кнопками; запрещённое → ⛔ + объяснение | MUST |
| FR-H1-07 | Мониторинг по расписанию: `granted` → уведомление; `requested` > 48 ч → черновик напоминания | MUST |
| FR-H1-08 | `/interns` для наставника и тимлида: X/5 по своим стажёрам | MUST |
| **FR-H1-09** | **Ни одного изменения в сервисах**: агенту доступны только инструменты чтения (см. 2_ARCHITECTURE §5) | MUST |

### 4.5. Метрики
- **Главная:** медианное время до фактического доступа ↓ в 2 раза; все 5 доступов к концу первой недели.
- **Поддерживающая:** обращения к наставнику по доступам ≈ 0.
- **Защитная:** 0 вызовов инструментов записи (журнал вызовов MCP).

## 5. H2 — «Кто есть кто»

### 5.1. Что делает и зачем
Отвечает на вопросы, с которыми стажёр идёт к наставнику или лиду: к кому обратиться и стоит ли, что за продукт и на каком он этапе, какой стек. Основание — кейс, стр. 7, задача 02: «научите помощника отвечать на вопросы о команде и инструментах с учётом контекста». Тимлид — первый контакт в неожиданных ситуациях. Нет ответа → вопрос уходит человеку через бота, ответ копится в FAQ.

### 5.2. 8 типов вопросов
| # | Тип | Источник | Ссылка |
|---|---|---|---|
| Q1 | Кто отвечает за <область>? | Карточка → `people.areas` | «Люди» |
| Q2 | К кому идти, если <ситуация>? | Карточка → `routing` | «Маршруты» |
| Q3 | Кто мой наставник / тимлид / первый контакт? | Карточка → `people` | «Люди» |
| Q4 | Можно ли писать <человеку> напрямую? | Карточка → `do_not_disturb` | «Кого не дёргать» |
| Q5 | На каком этапе проект? | Jira → эпик | Эпик |
| Q6 | Как моя задача связана с проектом? | Jira → задача + эпик | Задача, эпик |
| Q7 | Стек и инструменты команды? | Карточка → `tools` | «Инструменты» |
| Q8 | Где посмотреть <репозиторий / доску / чат>? | Карточка → `links` + статус H1 | Объект + статус |

### 5.3. Требования
| ID | Требование | Приоритет |
|---|---|---|
| FR-H2-01 | Карточка команды (YAML по схеме) загружается наставником или тимлидом через `/teamcard`, валидируется, версионируется | MUST |
| FR-H2-02 | `/ask` — меню из 8 типов; можно писать свободно | MUST |
| FR-H2-03 | Ответ только по карточке, FAQ и Jira, **со ссылкой на источник**, иначе «не нашёл» | MUST |
| FR-H2-04 | «Не нашёл» → [Спросить ответственного] [Спросить наставника] [Отложить] | MUST |
| FR-H2-05 | Эскалация — сообщение человеку через нашего бота (вопрос + контекст стажёра + что проверено); ответ — стажёру | MUST |
| FR-H2-06 | Ответ человека с его одобрения → FAQ; повторный вопрос закрывается из FAQ | SHOULD |
| FR-H2-07 | Вне пула → меню; HR-темы → контакт HR BP; чужая команда → отказ | MUST |
| FR-H2-08 | [Помогло] [Не помогло] под каждым ответом | MUST |

### 5.4. Метрики
- **Главная:** ≥ 70 % вопросов закрыто с «помогло».
- **Качество:** верный тип вопроса ≥ 90 %; выдуманные ответы ≤ 5 %.
- **Защитная:** обращения к тимлиду не растут.

│   ├── «что с моими доступами?» → 5 инструментов ✅ / ⬜ [Где запросить][Я запросил] / ⏳ / ⛔

└── Служебное: help · clarify · out_of_scope

## 9. Доказательная база (для презентации)

Внешние данные (не про стажёров Авито — на защите говорим «в индустрии»):
- **61 %** разработчиков тратят больше 30 минут в день на поиск ответов; **53 %** — ожидание ответов ломает рабочий процесс ([Stack Overflow 2024](https://survey.stackoverflow.co/2024/professional-developers)).
- **69 %** теряют **8+ часов в неделю** на неэффективность, среди причин — нехватка документации ([Atlassian / DX 2024](https://www.atlassian.com/blog/developer/developer-experience-report-2024)).
- Только **12 %** сотрудников считают онбординг в своей компании хорошим; при участии руководителя шанс отличного онбординга в **3,4 раза** выше ([Gallup](https://www.gallup.com/workplace/247172/problems-onboarding-program.aspx)).
- Microsoft (267 новичков): ключевые проблемы — **доступ к ПО** и связь с командой ([Microsoft Research](https://arxiv.org/pdf/2011.08130v1.pdf)).
- Backend-стажёр Авито: растерянность в первые недели и **запрос доступов** ([Хабр](https://habr.com/ru/post/550246)).

Свои данные: опрос стажёров (30+ ответов) и юзабилити-тест «вручную против бота» — см. [3_ROADMAP.md](3_ROADMAP.md).

**Вопросы, отправленные организаторам (10.11):** ограничения на каналы; «инструмент отслеживания прогресса»; формирование целей стажёра; ИИ-крон и MCP; приоритет «стажёр или наставник»; разбивка 40–48 ч; устройство корпоративных заявок; состав жюри. Ответов пока нет.
