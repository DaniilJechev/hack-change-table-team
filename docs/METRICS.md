# Метрики бота и эффект для наставника

Согласованный каталог, 15.11.2026. Этот документ **не добавляет события, SQL views
или панели**. Статусы ниже отделяют существующий сбор от расчётов и будущих работ.
Главная цель продукта — сократить рутинные часы наставника на стажёра.

## 1. Что именно измеряем

- Бот наблюдает обращения внутри своих каналов, результаты операций и явные реакции.
- Время наставника и обращения в личку вне бота напрямую не наблюдаются.
- Полезный ответ, клик, отсутствие эскалации и подтверждённое решение — разные сигналы.
- Ход диалога не равен отдельному вопросу: уточнения и повторы могут относиться к одной проблеме.
- Отсутствие события может означать отказ записи; TraceSink не блокирует ответ при сбое backend.

Основные продуктовые показатели: подтверждённые самостоятельные решения, эскалации,
повторное использование знаний, самостоятельные доработки H4. Фактические часы требуют
отдельного измерения; оценка часов требует явной модели и калибровки.

## 2. Уже существующие агрегаты

SQL-источники: [00005_stage_four.sql](../backend/migrations/00005_stage_four.sql),
[00007_agent_traces.sql](../backend/migrations/00007_agent_traces.sql).
Панели: [ai-buddy.json](../infra/grafana/dashboards/ai-buddy.json).

| Агрегат | Что есть сейчас | Ограничение |
|---|---|---|
| `metrics_briefs` | Отправленные, прочитанные, с кликом; read_percent/clicked_percent | Sent-брифы пользователей intern; общий срез без временного разреза |
| `metrics_helpful` | Число оценок, положительных оценок, их доля; H2/H3, bot/human | Доля только среди оценённых; не подтверждает решение |
| `metrics_access` | Завершённые запросы и среднее время от отметки до снимка granted | Наблюдаемое время обнаружения; не время работы наставника; зависит от частоты опроса |
| `metrics_mcp` | Число вызовов по сценарию/серверу/инструменту/исходу | Отказ политики не обязательно ошибка продукта; нет стоимости человеческой работы |
| `metrics_agent` | Ходы по UTC-дню/пути, fallback %, avg/p95 latency, avg tool_calls | Сейчас смешивает demo/live и роли; путь и case не описывают весь составной вопрос |

Grafana получает только разрешённые агрегаты. Новые разрезы проектируются как отдельные
агрегаты; доступ к raw-трейсам, текстам и таблицам пользователей ей не выдаётся.

## 3. Можно вывести из уже сохраняемых данных

Это доступность исходных данных, **не наличие готовой панели или проверенного запроса**.
Временные фильтры и нужные разрезы требуют дополнительной агрегации.

| ID | Показатель и формула | Источник / единица | Ограничение |
|---|---|---|---|
| BOT-01 | Полезные ответы: число уникальных сохранённых ответов с bot_helpful=true | questions, отдельно H2/H3; ответ | Считаются сохранённые ответы, не все реплики модели |
| BOT-02 | Полезность = положительные / все ненулевые оценки | questions, capability; ответ | Показывать вместе со знаменателем и охватом |
| BOT-03 | Охват оценками = оценённые / сохранённые ответы с непустым bot_answer | questions; ответ | Автоматические chat-ответы без записи сюда не входят |
| BOT-04 | Эскалации: число уникальных вопросов с assigned_to | questions; вопрос | created_at — время создания вопроса, не точное время назначения; доступна когорта созданных вопросов с текущим назначением |
| BOT-05 | Использование FAQ: число ходов с источником FAQ в turn.answer.sources | agent_traces.turn; ход | Считать ход один раз, даже при нескольких FAQ-ссылках; это использование, не предотвращённое обращение |
| BOT-06 | Повторное использование записи FAQ: число ходов с её source ID | agent_traces + faq_entries; FAQ/ход | Отделять повторные уточнения и synthetic; исходы вопросов пока неизвестны |
| BOT-07 | CTR брифа = sent-брифы с ≥1 click / все sent-брифы | briefs + brief_events; бриф | Несколько кликов не увеличивают числитель; зависит от настроенного редиректа |
| BOT-08 | Реакция на бриф = первый допустимый сигнал − sent_at; median/p90 | briefs + brief_events; минуты | Считать только сигналы после доставки; непрочитанные показывать отдельно, они не имеют нулевой задержки |
| BOT-09 | H4: число сохранённых проверок до первого passed | История H4; проверка/группа версий | Нужна осторожная группировка одной презентации; повтор того же digest не считать новой доработкой |
| BOT-10 | H4: доля проверок passed и доля версий с успешной доставкой файла и отчёта | История H4, passed/delivery_*; версия | Passed, отметка прогресса и доставка — независимые состояния; это ещё не часы наставника |

Для BOT-04 отдельное число назначений наставнику следует отличать от передач другому
ответственному. Привязка назначения к событийному времени пока не гарантирована.
BOT-09/10 выводятся из сохранённой истории, которая может истечь через семь дней;
история по пользователю сама по себе не даёт надёжный ID отдельной презентации.

## 4. Требуют новых событий или связей

Эти метрики утверждены как направление дальнейшей реализации. В текущем коде не
заявляются готовыми. Реализация проходит отдельную OpenSpec-дельту и тесты.

| ID | Показатель | Формула / данные |
|---|---|---|
| OUT-01 | Подтверждённое самостоятельное решение | Уникальные problem_id с явным «решил без человека» / вопросы с известным исходом |
| OUT-02 | Охват известными исходами | problem_id с явным исходом / все зарегистрированные problem_id |
| OUT-03 | Доля эскалаций | problem_id с escalation_created / все problem_id соответствующей когорты |
| OUT-04 | Эскалация после заявленного успеха | problem_id с human_needed после solved_without_human / подтверждённые самостоятельные решения с завершённым окном наблюдения |
| OUT-05 | Доступ без наблюдаемого вмешательства наставника | Завершённые заявки без mentor_intervention внутри бота / завершённые заявки |
| OUT-06 | Самостоятельная доработка H4 | Презентации с цепочкой failed → новая версия → passed до передачи / презентации с исходным failed и достаточным окном наблюдения |

Минимальные новые данные:

- `problem_id`: создаётся кодом, связывает ответ, уточнения, оценки и эскалацию;
- исходы `solved_without_human`, `human_needed`; время и автор подтверждения;
- `escalation_created`: адресат/роль и время, без дублирования текста в метриках;
- `request_id`, `mentor_intervention`: заявка и зарегистрированное вмешательство;
- `presentation_id`, `version_id`: одна работа и её разные версии;
- доверенные `demo`, `channel`, team/role, время; идемпотентный event_id.

Пример кнопок: «Решил вопрос», «Нужна помощь». Неответившие остаются с неизвестным
исходом. Если 55 из 75 известных исходов самостоятельные, а всего 100 вопросов,
OUT-01=55/75, OUT-02=75/100; обе доли публикуются вместе.
OUT-05 отражает только видимые вмешательства; переписка вне бота остаётся неизвестной.
Окно OUT-04 следует выбрать до анализа и указывать на панели; недавно закрытые вопросы
с незавершённым окном не включаются в его знаменатель.

## 5. Правила расчёта

1. Единица определяется заранее: ответ, ход, проблема, бриф, заявка или презентация.
   Для продуктовых исходов нельзя складывать ходы как разные проблемы.
2. Период — неделя в Europe/Moscow; хранение timestamp UTC. У существующей панели
   metrics_agent UTC-день, поэтому сравнение дневных графиков требует приведения.
3. Demo/live и роли разделяются; сравнение желательно по команде, категории вопроса
   и неделе стажировки. Пользовательские ID и raw-тексты не выводятся в Grafana.
4. У каждой доли показываются числитель, знаменатель, период и покрытие. При нуле
   знаменателя — «нет данных», не 0 % успешности. Для маленьких групп не делать вывод об эффекте.
5. Для времени использовать median/p90 и число наблюдений. Неуспехи/незавершённые
   показывать отдельно: удаление их из выборки создаёт впечатление ускорения.
6. Дедуплицировать event_id, запросы и одинаковые версии. При compound-ответе
   case_name первого инструмента не считать полной тематической классификацией.
7. Срез по назначению/исходу сейчас и событие в периоде — разные выборки.
   Фиксировать время построения и правило зрелости когорты.

## 6. Текущие пробелы телеметрии

В demo часть событий H1/H2 живёт в SeedData, а трассы при настроенном backend
пишутся в PostgreSQL. Графовые трассы не покрывают автоматически все прямые
команды, H4, интерактивные операции и legacy-путь. События failed-записи могут потеряться.
Retention agent_traces по умолчанию 30 дней; H4 — 7 дней. Для более длинного пилота
нужны корректно сохраняемые обезличенные агрегаты и отдельное решение о хранении.

Нет общего problem_id для ответа и последующей эскалации. Поэтому текущий счётчик
вопросов с назначением нельзя делить на число ходов и называть долей самообслуживания.
Нет полного наблюдения участия наставника вне бота и фактического выполнения задачи
после клика. BOT-01/05/07 показывают сигналы пользы, но не доказанную экономию часов.

## 7. Оценка предотвращённых трудозатрат

После реализации problem_id и подтверждённых исходов:

```text
Оценка часов = Σ(самостоятельно решённые проблемы категории ×
                калиброванные минуты наставника для категории) / 60
```

Коэффициенты получают из небольшого замера/опроса наставников, версионируют и
публикуют вместе с диапазоном оценки. Одну проблему считают один раз; нельзя одновременно
начислять ей экономию за ответ, FAQ, клик и H4. Разовые расходы настройки и регулярные
расходы проверки/исправления бота учитываются отдельно. Эта модель не доказывает,
что каждый вопрос в отсутствие бота обязательно попал бы наставнику.

Фактическая цель пилота: рутинные минуты наставника на стажёра в неделю до/после,
с учётом недели стажировки и состава задач. Значение «снижение ≥25 %» из продукта —
гипотеза. Текущих бот-событий недостаточно, чтобы объявить её достигнутой.

## 8. Первый дашборд следующей итерации

1. BOT-01/02/03: полезные ответы и покрытие оценками.
2. BOT-04: эскалации с корректной когортой и ролью адресата.
3. BOT-05/06: использование FAQ и отдельных записей.
4. OUT-01/02/03 после новых событий: самостоятельность, покрытие исходов и эскалации.
5. BOT-09/OUT-06: автоматические проверки и подтверждённая доработка H4.

Рядом — технические причины: latency, ошибки источников, denied-вызовы и fallback.
Fallback может дать полезный проверенный ответ и сам по себе не является провалом.
