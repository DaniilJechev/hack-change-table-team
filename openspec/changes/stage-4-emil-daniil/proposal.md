# Этап 4: H0 (утренний бриф) и H3 (ответы по playbook) — части Эмиля и Даниила

## Why
По roadmap Этап 4 даёт рабочие H0 и H3 в Telegram и фриз фич. Пользователь поручил выполнить части Эмиля и Даниила в отдельной ветке; приёмка — на синтетических фикстурах, как на Этапах 1–3.

## What Changes
- H0: сборщики изменений GitHub, Jira и Google Calendar (календарь — сравнением снимков), нормализация в `BriefItem`, ранжирование и лимит 5 пунктов с кнопкой «Ещё N», главное действие по правилу, проверка ссылок кодом, рендер (LLM только переформулирует строки по `item_id`, шаблон — запасной вариант), расписание, `/brief`, «что нового?», бриф по одному источнику, [✅ Прочитал] 👍/👎, ответ на бриф как сигнал чтения, `/stats`, `/settings`.
- H3: снимок `avito-tech/playbook` на коммите `0c1d2aa`, разбиение на фрагменты по заголовкам со ссылкой на GitHub с якорем, индекс, `playbook_qa` с ответом только по найденным фрагментам, отказ «В playbook этого нет» с кнопкой [Спросить наставника], пометка об актуальности, запасной вариант без LLM.
- H3, режимы поиска — новая переменная `RAG_SEARCH_MODE`: `bm25` (по умолчанию; без модели и без БД), `vector` (эмбеддинги e5 + pgvector), `rrf` (объединение обоих списков). В режиме `bm25` модель эмбеддингов не загружается в память. Зависимости e5 и pgvector вынесены в необязательный набор `rag`.
- Демо: третий шаг «следующее утро», фиксированные часы синтетического дня, базовый снимок календаря; фикстуры H0 для всех шагов.
- Evals H3: метрики поиска по трём режимам на наборе из 35 вопросов.

## Impact
`agent/`, `seed/`, `fixtures/`, `data/playbook/`, `evals/`, документация и OpenSpec. В зоне Ильи изменены только точки подключения: `agent/Dockerfile` (аргумент сборки `AGENT_EXTRAS`), `docker-compose.yml` (переменные `RAG_*`, `BRIEF_*`, `REDIRECT_BASE_URL`, том для модели), `Makefile` (`ingest`, `setup-rag`, `ingest-compose`), `.env.example`. Go backend не меняется.

Отступления от исходных формулировок и зависимости (оформлены дельтами ниже):
- FR-H3-01 требовал хранить фрагменты только в pgvector. Теперь основной индекс — файл в пакете агента (нужен демо-режиму без БД), а таблица `rag_chunks` в pgvector создаётся и заполняется командой индексации только для режимов `vector` и `rrf`. Таблицу создаёт сама индексация (`CREATE TABLE IF NOT EXISTS`), а не миграция backend.
- Редирект `/r/<item_id>` и хранение снимков календаря — часть Ильи на Этапе 4. До неё агент отдаёт прямые ссылки (или ссылки через `REDIRECT_BASE_URL`, если он задан), а снимок календаря, момент последнего отправленного брифа, статистику и настройки держит в памяти процесса; сами брифы и события чтения уже пишутся в backend через REST.
- Внешние идентификаторы объектов (репозиторий, проект, календарь) в каталоге backend по-прежнему отсутствуют — в живом режиме источники без них помечаются как недоступные.
- В репозитории `avito-tech/playbook` нет файла лицензии; снимок хранится с указанием источника и коммита.
