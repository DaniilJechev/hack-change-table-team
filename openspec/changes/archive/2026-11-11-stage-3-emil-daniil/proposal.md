# Этап 3: H1 (доступы) и H2 (кто есть кто) — части Эмиля и Даниила

## Why
По roadmap Этап 3 даёт рабочие H1 и H2 в Telegram. Пользователь поручил выполнить части Эмиля и Даниила в отдельной ветке, продолжая приёмку на синтетических фикстурах.

## What Changes
- H1: проверка 5 объектов инструментами чтения (GitHub `list_repository_collaborators`, Jira `jira_search_assignable_users`, Miro `content_item_list_roles`, Calendar `list-events`, Telegram `getChatMember`), статусы, [Где запросить] / [Я запросил], доступы под задачу, мониторинг изменений, черновик напоминания, `/interns`.
- H2: ответы team_q1–q8 по карточке, FAQ и Jira со ссылками; «не нашёл» с эскалацией через бота, ответ человека, [Сохранить в FAQ], [Помогло]/[Не помогло].
- Слой данных агента: `SeedData` (демо, в памяти, с правами как в backend) и `BackendData` (чтение через `buddy-mcp`, запись через REST).
- Фикстуры шагов для H1/H2, в seed — логины пользователей в 5 инструментах и цели проверок (`targets`).
- Evals: H2 — 40 вопросов (8 типов × 5), H3 — 35 вопросов (30 по снимку playbook с файлом-источником, 5 вне корпуса).
- Уточнения требований (дельты ниже): статус `unknown` при ошибке проверки, черновик напоминания текстом, формулировка отказа `/interns`, эпик демо — ORD-100.

## Impact
Только `agent/`, `seed/`, `fixtures/`, `evals/`, документация и OpenSpec. Go backend, Compose и CI Ильи не меняются.

Зависимости от backend (Илья) для живого режима:
- в каталоге доступов нет внешних идентификаторов объектов (owner/repo, project_key, board_id, calendarId, chat_id) — агент берёт их из `targets` демо-бандла;
- нет связи user_id → Telegram chat: эскалация доставляется только тем, кто открывал бота в этом процессе;
- `/teamcard`, REST FAQ/эскалаций и статусы в `interns_list` — зона Ильи.

Имена объектов в сценариях спецификаций (orders-api, «ORD-90 Planning») иллюстративны; демо использует синтетические `orders-onboarding`, `demo-board-orders`, эпик ORD-100.
