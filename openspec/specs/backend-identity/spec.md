# backend-identity Specification

## Purpose
Серверная часть Этапа 1: миграции и синтетические пользователи, одноразовые
приглашения и REST-привязка Telegram, служебная авторизация и готовность БД,
опциональный запуск готовых MCP-серверов с проверкой инструментов чтения.

## Requirements

### Requirement: NFR-DB-1 Миграции и синтетические пользователи
Backend SHALL применять встроенные миграции goose перед обслуживанием запросов.
Импорт `seed/users.yaml` SHALL быть атомарным и идемпотентным, сохранять привязки
Telegram и использованные приглашения, проверять роли и принадлежность наставника
той же команде. Невалидный seed MUST отклоняться целиком.

#### Scenario: Повторный запуск
- **WHEN** миграции и импорт одного seed выполнены дважды
- **THEN** пользователи не дублируются, привязки сохраняются

#### Scenario: Невалидный seed
- **WHEN** seed содержит неизвестную роль или наставника чужой команды
- **THEN** импорт отклоняется без частичной записи

### Requirement: NFR-AUTH-API-1 Одноразовая привязка
Служебный `POST /api/v1/auth/bind` SHALL принимать только `code`,
`telegram_user_id` и `telegram_chat_id`, проверять положительные ID личного чата
и возвращать профиль с ролью и командой из БД. Приглашения SHALL выпускаться
локальной командой backend для существующего пользователя, иметь срок действия
и криптографически случайный код; в БД MUST храниться только его SHA-256.
Погашение приглашения и привязка SHALL быть атомарными. Использованный,
просроченный или неизвестный код SHALL давать одинаковую ошибку
`invalid_invitation`: «Код не подошёл, спроси наставника».
Существующая привязка Telegram MUST NOT переноситься на другого сотрудника.

#### Scenario: Верный код
- **WHEN** действующий код стажёра demo-orders передан с ID личного Telegram-чата
- **THEN** возвращается профиль стажёра demo-orders, код становится использованным

#### Scenario: Неверный или истёкший код
- **WHEN** передан неизвестный, использованный или просроченный код
- **THEN** возвращается invalid_invitation и привязка не создаётся

#### Scenario: Одновременное погашение
- **WHEN** два клиента одновременно предъявляют одно приглашение
- **THEN** успешно завершается ровно одна привязка

#### Scenario: Конфликт Telegram
- **WHEN** Telegram уже связан с другим сотрудником или сотрудник с другим Telegram
- **THEN** возвращается binding_conflict и приглашение остаётся неиспользованным

#### Scenario: Некорректный запрос
- **WHEN** запрос содержит неизвестные поля, лишний JSON, слишком большое тело или ID группового чата
- **THEN** возвращается invalid_request без изменения БД

### Requirement: NFR-AUTH-API-2 Служебная авторизация и определение пользователя
Все `/api/v1/*` SHALL требовать `X-Buddy-Key` и сравнивать ключ без утечки по времени.
Пустой настроенный ключ SHALL закрывать API с 503. `GET /api/v1/auth/telegram/{id}`
SHALL возвращать только профиль связанного пользователя, 404 для неизвестного ID.
Секреты, коды приглашений и ошибки драйвера MUST NOT попадать в HTTP-ответы.
`GET /ready` SHALL проверять БД; `/health` SHALL сохранять действующий контракт stage=0.

#### Scenario: Нет служебного ключа
- **WHEN** ключ отсутствует или неверен
- **THEN** запрос отклоняется с 401 до обращения к данным

#### Scenario: API без настроенного ключа
- **WHEN** служебный ключ пуст
- **THEN** API возвращает 503

#### Scenario: Определение пользователя
- **WHEN** агент запрашивает привязанный Telegram ID
- **THEN** получает профиль из БД; непривязанный ID даёт 404

#### Scenario: БД недоступна
- **WHEN** запрос к БД завершился ошибкой
- **THEN** readiness и API возвращают 503 без технических подробностей

### Requirement: NFR-MCP-BOOT-1 Опциональный запуск серверов чтения
Jira и Calendar SHALL запускаться отдельной опциональной Compose-конфигурацией,
не требуемой для `make up` и `make demo`. GitHub MCP SHALL быть доступен в образе
агента для запуска через stdio без Docker socket. Версии SHALL быть закреплены;
ограничения чтения MUST задаваться конфигурацией проекта: GitHub --read-only,
Jira READ_ONLY_MODE=true и ENABLED_TOOLS, Calendar ENABLED_TOOLS чтения.
Проверка tools/list SHALL отклонять неожиданные инструменты и требовать наличие
ожидаемых инструментов; она MUST NOT вызывать корпоративные инструменты.

#### Scenario: Демо без аккаунтов
- **WHEN** выполняется make demo без ключей GitHub/Jira/Google
- **THEN** основной стек работает без запуска внешних MCP

#### Scenario: Инвентаризация инструментов
- **WHEN** выполняется проверка готовых MCP с синтетической конфигурацией
- **THEN** tools/list содержит только настроенные инструменты чтения
