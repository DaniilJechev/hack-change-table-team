# h1-access Specification

## Purpose
Мониторинг доступов (H1): агент показывает, к каким из 5 инструментов (GitHub, Jira, Miro, Google Calendar,
Telegram) у стажёра есть доступ, объясняет, где запросить недостающее, отслеживает появление доступа
и напоминает о зависших запросах. Агент ничего не меняет в сервисах.

## Requirements

### Requirement: FR-H1-01 Пакет доступов роли
Для роли «Backend-стажёр» система SHALL определять 5 объектов доступа из каталога `access_catalog_get`: репозиторий GitHub, проект Jira, доску Miro, регулярные встречи команды в Google Calendar и командный чат Telegram.

#### Scenario: Первый вход стажёра
- **WHEN** Даниил впервые привязал аккаунт
- **THEN** бот показывает статус по всем 5 объектам и кнопки [Где запросить] для отсутствующих

### Requirement: FR-H1-02 Статусы доступа
Каждому объекту SHALL присваиваться один статус: `granted`, `missing`, `requested`, `stale`, `forbidden` или `unknown`. Статус `unknown` MUST ставиться, когда проверку в инструменте выполнить не удалось; он не считается отсутствием доступа и не меняет сохранённый статус.

#### Scenario: Запрошен более 48 часов назад
- **WHEN** стажёр нажал [Я запросил] для доски Miro 3 дня назад и доступа всё ещё нет
- **THEN** статус доски Miro — `stale`

#### Scenario: Инструмент недоступен
- **WHEN** вызов `content_item_list_roles` завершился ошибкой
- **THEN** статус доски — `unknown`, и бот не предлагает запросить доступ повторно

### Requirement: FR-H1-03 Проверка в самом инструменте
Наличие доступа MUST проверяться в самом инструменте инструментами чтения: GitHub — `list_repository_collaborators` или `get_team_members`; Jira — `jira_search_assignable_users`; Miro — `content_item_list_roles`; Google Calendar — участие в регулярных встречах команды через `list-events`; Telegram — `getChatMember`.

#### Scenario: Стажёр есть среди участников доски
- **WHEN** `content_item_list_roles` для доски «ORD-90 Planning» содержит Miro-аккаунт Даниила
- **THEN** статус доски — `granted`

#### Scenario: Стажёра нет в чате
- **WHEN** `getChatMember` для командного чата возвращает статус `left`
- **THEN** статус чата — `missing`, и бот советует попросить наставника добавить в чат

### Requirement: FR-H1-04 Где запросить и отметка «я запросил»
Для статуса `missing` бот SHALL показывать, где и у кого запросить доступ (из каталога), и кнопку [Я запросил], которая MUST сохранять отметку с датой через REST бэкенда.

#### Scenario: Нет доступа к Miro
- **WHEN** у Даниила нет доступа к доске Miro
- **THEN** бот показывает ссылку на запрос доступа, владельца Олега и кнопку [Я запросил]

### Requirement: FR-H1-05 Доступы под задачу
По кнопке [Что нужно?] или вопросу о задаче агент SHALL получить задачу через `jira_get_issue`, определить упомянутые объекты из 5 инструментов и показать статус только по ним.

#### Scenario: ORD-118
- **WHEN** стажёр спрашивает «Какие доступы нужны для ORD-118?», а в задаче упомянуты репозиторий orders-api и доска «ORD-90 Planning»
- **THEN** бот показывает: GitHub orders-api ✅, Miro «ORD-90 Planning» ⬜ [Где запросить]

#### Scenario: Все доступы есть
- **WHEN** все объекты из задачи имеют статус `granted`
- **THEN** бот отвечает «Доступов для ORD-118 хватает ✅»

### Requirement: FR-H1-06 Неоднозначность и запрещённые объекты
При нескольких подходящих объектах бот SHALL предлагать выбор кнопками; объект, запрещённый роли в каталоге, MUST показываться как ⛔ с объяснением и без кнопки запроса.

#### Scenario: Два репозитория
- **WHEN** в задаче написано «сервис заказов», а в каталоге есть orders-api и orders-admin
- **THEN** бот спрашивает «Какой репозиторий?» с кнопками [orders-api] [orders-admin]

#### Scenario: Запрещённый репозиторий
- **WHEN** задача упоминает prod-репозиторий, запрещённый стажёрам
- **THEN** бот показывает ⛔ и текст «стажёрам не выдаётся, обсуди с наставником»

### Requirement: FR-H1-07 Мониторинг по расписанию
Планировщик SHALL периодически перепроверять объекты со статусами `missing`, `requested` и `stale`; при появлении доступа бот MUST уведомить стажёра, а при статусе `stale` — предложить черновик напоминания владельцу текстом для копирования, который стажёр отправляет сам.

#### Scenario: Доступ появился
- **WHEN** при очередной проверке Даниил появился среди участников доски Miro
- **THEN** бот пишет «Доступ к Miro появился ✅» со ссылкой на доску

#### Scenario: Зависший запрос
- **WHEN** статус доски перешёл в `stale`
- **THEN** бот присылает черновик напоминания Олегу и сам ничего не отправляет Олегу

### Requirement: FR-H1-08 Сводка для наставника
Команда `/interns` SHALL показывать наставнику статусы доступов его стажёров (X из N и объекты в ожидании); стажёр MUST получать отказ.

#### Scenario: Наставник
- **WHEN** Анна отправляет `/interns`
- **THEN** бот показывает «Даниил — 4/5, ждёт: demo-orders-miro» и не показывает стажёров других наставников

#### Scenario: Стажёр
- **WHEN** Даниил отправляет `/interns`
- **THEN** бот отвечает «Сводка стажёров доступна только наставнику или тимлиду»

### Requirement: FR-H1-09 Никаких изменений в сервисах
Агент SHALL NOT создавать заявки, выдавать права, приглашать в чаты или менять доски; в кейсах H1 MUST использоваться только инструменты чтения.

#### Scenario: Попытка выдать доступ
- **WHEN** LLM в кейсе `access_status` запрашивает вызов `board_share`
- **THEN** код отклоняет вызов и записывает его в журнал `mcp_calls`

### Requirement: FR-H1-10 Проверки доступов без LLM
Проверки H1 SHALL выполняться кодом по каталогу и целям объектов, без LLM; каждый вызов MUST проходить через белый список инструментов чтения кейса. Бюджет RT-05 (3 вызова) относится к шагам LLM и не ограничивает программную проверку 5 объектов.

#### Scenario: Пять проверок за один ответ
- **WHEN** стажёр спрашивает «Что с моими доступами?»
- **THEN** агент вызывает по одному инструменту чтения на каждый из 5 объектов и показывает статусы со ссылками

### Requirement: FR-H1-11 Подтверждённое членство
Проверка SHALL сопоставлять логин с полями участника, а не произвольным текстом ответа. Calendar MUST проверять attendees действующей встречи; совпадение в organizer, описании или отменённой встрече не подтверждает участие. Неизвестная форма ответа SHALL давать unknown.

#### Scenario: Логин только в описании
- **WHEN** логин найден в описании объекта, но отсутствует в участниках
- **THEN** доступ не считается подтверждённым

### Requirement: FR-H1-12 Восстановление базы сравнения
После перезапуска обработчика мониторинг SHALL использовать последний сохранённый снимок, если он доступен; unknown MUST NOT подменять подтверждённый статус. Если снимка нет, первая проверка SHALL оставаться исходной точкой. Возобновление проверки пользователей после запуска происходит при их обращении к боту.

#### Scenario: Перезапуск обработчика
- **WHEN** сохранён missing, обработчик пересоздан, а инструмент теперь подтверждает granted
- **THEN** мониторинг сообщает о появившемся доступе и сохраняет новый снимок
