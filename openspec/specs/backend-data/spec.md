# backend-data Specification

## Purpose
Наши данные AI-buddy в Go-backend: собственный MCP-сервер `buddy-mcp` с шестью инструментами чтения,
атомарная загрузка синтетических seed-данных (пользователи, карточка команды, каталог доступов)
и REST для записи только наших данных — брифов и их событий, снимков доступов, вопросов, ответов,
FAQ и отметок «я запросил». Пользователь, роль и команда определяются сервером на каждом запросе.

## Requirements

### Requirement: ST2-MCP-1 Наши инструменты чтения
Backend SHALL предоставлять `/mcp` через официальный MCP Go SDK и Streamable HTTP,
с инструментами user_profile_get, team_card_get, team_faq_search,
access_catalog_get, access_marks_get, interns_list и без инструментов записи.
Запросы MUST проверять X-Buddy-Key и X-Buddy-User; профиль, роль и команда
загружаются из БД заново на каждом HTTP-запросе. Аргументы не задают чужую команду.

#### Scenario: Шесть инструментов
- **WHEN** SDK-клиент подключается с действительными заголовками
- **THEN** tools/list возвращает ровно шесть инструментов чтения, каждый вызывается

#### Scenario: Изоляция пользователей
- **WHEN** передан неизвестный пользователь, неверный ключ или запрос чужих данных
- **THEN** доступ отклоняется без раскрытия данных и ошибок PostgreSQL

#### Scenario: Сводка наставника
- **WHEN** наставник вызывает interns_list
- **THEN** получает только своих стажёров; тимлид — стажёров своей команды; стажёр получает отказ

### Requirement: ST2-DATA-1 Загрузка данных команды
Локальная команда seed SHALL загружать существующие YAML карточки и каталога
вместе с пользователями атомарно; повтор SHALL сохранять привязки, отметки и FAQ.
Невалидные данные MUST отклоняться целиком. Пустые FAQ и объекты допустимы.

#### Scenario: Повтор seed
- **WHEN** команда seed запускается дважды
- **THEN** данные доступны через MCP без дубликатов и без потери пользовательских записей

#### Scenario: Ошибка данных
- **WHEN** карточка или каталог невалидны или относятся к неизвестной команде
- **THEN** импорт откатывается, сообщение указывает поле без содержимого секретов

### Requirement: ST2-REST-1 Хранение наших данных
REST SHALL сохранять и читать брифы и их события, снимки доступов, вопросы,
ответы и FAQ и отметки «я запросил», с авторизацией пользователя и изоляцией команд.
Повтор записи с тем же идентификатором и содержимым SHALL быть идемпотентным;
переиспользование идентификатора с другим содержимым MUST отклоняться.
Повтор отметки MUST сохранять первоначальную дату. Запрещённый объект нельзя отметить.
FAQ SHALL публиковаться только автором сохранённого ответа с явным согласием.

#### Scenario: Повтор отметки
- **WHEN** стажёр повторно отмечает один объект
- **THEN** остаётся первоначальная дата запроса

#### Scenario: Чужие записи
- **WHEN** пользователь обращается к брифу или вопросу другого пользователя без разрешения
- **THEN** запись недоступна

#### Scenario: Согласие автора
- **WHEN** автор подтверждает сохранение собственного ответа в FAQ
- **THEN** FAQ доступен своей команде; без согласия или от другого автора запись не создаётся

#### Scenario: Событие брифа
- **WHEN** событие прочтения повторяется
- **THEN** сохраняется одно событие и первоначальное read_at
