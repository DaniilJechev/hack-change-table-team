# platform Specification

## Purpose
Общие свойства AI-buddy, на которые опираются все гипотезы: вход в бот и роли, режим «только чтение»,
ссылки на источники, демо-режим, настройка LLM, отказоустойчивость, журналирование и метрики.

## Requirements

### Requirement: NFR-AUTH-1 Привязка аккаунта по коду приглашения
Бот SHALL привязывать Telegram-аккаунт к сотруднику и роли (стажёр, наставник, тимлид) по одноразовому коду из команды `/start <код>`.

#### Scenario: Верный код
- **WHEN** Даниил отправляет `/start` с действующим кодом стажёра команды demo-orders
- **THEN** бот привязывает аккаунт к роли «стажёр» и команде demo-orders и показывает меню

#### Scenario: Неверный код
- **WHEN** пользователь отправляет `/start` с несуществующим или использованным кодом
- **THEN** бот отвечает «Код не подошёл, спроси наставника» и не создаёт привязку

### Requirement: NFR-RO-1 Только чтение корпоративных сервисов
Агент SHALL NOT выполнять вызовы, изменяющие данные в GitHub, Jira, Google Calendar, Miro или Telegram; ему MUST быть доступны только инструменты чтения из белого списка кейса.

#### Scenario: Попытка вызвать инструмент записи
- **WHEN** LLM в ответе запрашивает вызов инструмента, которого нет в белом списке текущего кейса (например, `board_share` в Miro)
- **THEN** код агента отклоняет вызов, не передаёт его в MCP-сервер и записывает попытку в журнал `mcp_calls`

#### Scenario: Конфигурация MCP-серверов
- **WHEN** запускаются MCP-серверы проекта
- **THEN** github-mcp-server работает с `--read-only`, mcp-atlassian — с `READ_ONLY_MODE=true`, google-calendar-mcp — с `ENABLED_TOOLS` только из инструментов чтения, а `buddy-mcp` не публикует ни одного инструмента записи

### Requirement: NFR-RO-2 Журнал вызовов MCP
Агент SHALL записывать каждый вызов MCP-инструмента в журнал с кейсом, сервером, инструментом, пользователем и результатом.

#### Scenario: Проверка отсутствия записей
- **WHEN** запускается тест безопасности после прогона всех сценариев
- **THEN** в журнале `mcp_calls` нет ни одного вызова инструмента записи

### Requirement: NFR-LINK-1 Ссылка на источник в ответах
Каждый факт о данных внешнего сервиса или документа в ответе бота MUST сопровождаться ссылкой на конкретный объект; ссылки подставляет код, а не LLM.

#### Scenario: LLM вернула ссылку на несуществующий объект
- **WHEN** Executor вернул цитату с идентификатором, которого нет среди полученных данных
- **THEN** код удаляет этот фрагмент ответа, а если фактов со ссылками не осталось — показывает ответ «не нашёл»

### Requirement: NFR-DEMO-1 Демо-режим без внешних аккаунтов
При `DEMO_MODE=true` система SHALL отвечать на вызовы MCP записанными ответами из `fixtures/` и проходить полный демо-сценарий без доступа к GitHub, Jira, Google и Miro.

#### Scenario: Запуск жюри
- **WHEN** проверяющий запускает `docker compose up` с `DEMO_MODE=true` на чистой машине
- **THEN** бот проходит сценарий H0–H3, используя фикстуры, и ни разу не обращается к внешним MCP-серверам

#### Scenario: Переключение шага сценария
- **WHEN** ведущий отправляет `/demo next`
- **THEN** агент переключается на фикстуры следующего шага (например, «доступ к Miro появился»)

#### Scenario: Нет фикстуры
- **WHEN** в демо-режиме вызывается инструмент с аргументами, для которых нет фикстуры
- **THEN** вызов возвращает ошибку «нет данных», а кейс отрабатывает так же, как при недоступном источнике

### Requirement: NFR-DEMO-2 Запись фикстур
При `RECORD_MODE=true` агент SHALL сохранять ответы реальных MCP-серверов в `fixtures/` по ключу «сервер + инструмент + нормализованные аргументы».

#### Scenario: Запись ответа
- **WHEN** в режиме записи вызывается `jira_get_issue` для ORD-118
- **THEN** ответ сохраняется в файл фикстуры текущего шага, и в демо-режиме этот вызов возвращает тот же ответ

### Requirement: NFR-LLM-1 Провайдер LLM через окружение
Провайдер, модель LLM и модель эмбеддингов MUST задаваться переменными окружения `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY`, `EMBEDDINGS_MODEL`.

#### Scenario: Смена провайдера
- **WHEN** в `.env` меняются `LLM_PROVIDER` и `LLM_MODEL`
- **THEN** после перезапуска агент использует новый провайдер без изменения кода

### Requirement: NFR-FB-1 Работа без LLM
Каждый кейс SHALL иметь запасной вариант без LLM: Router — правила по командам и ключевым словам, Executor — шаблонный ответ.

#### Scenario: LLM недоступна
- **WHEN** запрос к LLM завершился ошибкой или превысил таймаут 20 секунд
- **THEN** бот отвечает по шаблону кейса и показывает те же кнопки, а не сообщение об ошибке

### Requirement: NFR-PERF-1 Отзывчивость интерфейса
Локальные действия бота (меню, кнопки без обращения к LLM) SHALL выполняться быстрее 1 секунды; во время обращения к LLM бот MUST показывать индикатор «печатает…».

#### Scenario: Нажатие кнопки меню
- **WHEN** стажёр нажимает кнопку меню
- **THEN** бот отвечает менее чем за 1 секунду

### Requirement: NFR-ERR-1 Недоступный источник
При недоступности MCP-сервера или внешнего сервиса бот SHALL показывать понятный статус и продолжать работу с остальными источниками.

#### Scenario: GitHub не отвечает
- **WHEN** github-mcp-server не отвечает во время сбора брифа
- **THEN** бриф отправляется без блока Git с пометкой «Данные из Git сейчас недоступны»

### Requirement: NFR-PRIV-1 Изоляция данных команд
Пользователь SHALL получать данные только своей команды; buddy-mcp MUST проверять пользователя на каждом вызове.

#### Scenario: Стажёр другой команды
- **WHEN** Кирилл (команда payments) спрашивает о карточке команды demo-orders
- **THEN** buddy-mcp не возвращает данные demo-orders, а бот отвечает, что может говорить только о своей команде

### Requirement: NFR-OUT-1 Вне области
Бот SHALL NOT отвечать по существу на вопросы о зарплате, медицинских и персональных данных и MUST давать контакт HR BP.

#### Scenario: Вопрос о зарплате
- **WHEN** стажёр спрашивает «Сколько я буду получать?»
- **THEN** бот отвечает «Это вопрос к HR BP» и даёт контакт

### Requirement: NFR-PERF-WAIT-1 Индикация длительного ожидания
Telegram-обработчик обычного LLM-запроса и H4 SHALL обновлять typing в фоновой задаче
с интервалом 4 секунды между успешным вызовом и следующим обновлением. Задержка
индикатора MUST NOT блокировать основную обработку. Сетевой/API-сбой индикатора MUST NOT
отменять результат. Завершение, ошибка или отмена обработчика MUST прекращать обновления.

#### Scenario: Долгая обработка
- **WHEN** LLM-запрос или H4 ожидает внешний ответ дольше одного интервала
- **THEN** typing отправляется повторно, цикл событий может обрабатывать другие действия

#### Scenario: Завершение и отмена
- **WHEN** обработчик завершён, выбросил исключение или отменён
- **THEN** фоновая задача индикации остановлена и не отправляет новые обновления

#### Scenario: Ошибка индикатора
- **WHEN** Telegram API индикатора возвращает сетевую ошибку
- **THEN** основная обработка продолжает возвращать результат независимо от этой ошибки
