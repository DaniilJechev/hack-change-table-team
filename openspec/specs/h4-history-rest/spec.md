# h4-history-rest Specification

## Purpose
Постоянная live-история проверок H4 через REST и PostgreSQL: изоляция пользователя,
срок хранения, поколения загрузок, атомарные стадии доставки и служебное разрешение
чата собственного наставника. Демо-история остаётся локальной и не требует backend.

## Requirements

### Requirement: H4-REST-1 История и поколения
REST SHALL хранить только собственные live-попытки H4 в PostgreSQL. POST invalidate SHALL атомарно повышать поколение загрузки и отменять старые кнопки. PUT проверки SHALL сохранять результат и разрешать актуальность только для текущего поколения. Истёкшие записи MUST удаляться при обращении. Срок задаётся H4_HISTORY_TTL_DAYS, по умолчанию 7 дней.

#### Scenario: Поздний результат и срок
- **WHEN** результат старой загрузки сохраняется после новой или запись истекла
- **THEN** старая кнопка не становится актуальной; истёкшая запись недоступна

### Requirement: H4-REST-2 Доставка и наставник
REST SHALL атомарно захватывать отдельные стадии file/report только актуальной пройденной проверки. Доставленные стадии MUST NOT захватываться повторно; unknown допускает повтор только с явным retry_unknown после предупреждения о возможной копии. Стадия sending MUST отклонять конкурентный захват. Служебный маршрут наставника SHALL отдавать только Telegram-чат собственного наставника в своей команде.

#### Scenario: Конкурентная отправка
- **WHEN** два запроса захватывают одну стадию доставки
- **THEN** только один получает захват, другой получает conflict

#### Scenario: Явный повтор неизвестного исхода
- **WHEN** стажёр подтвердил риск копии и запрашивается retry_unknown для стадии unknown
- **THEN** стадия переходит в sending; повторный конкурентный захват получает conflict
