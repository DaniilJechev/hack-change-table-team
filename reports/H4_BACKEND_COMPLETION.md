# H4: история через REST и PostgreSQL

Дата: 14 ноября 2026. Ветка: `codex/h4-completion-plan`.

## Реализовано

- Миграция `00008_equator_history.sql`: поколения загрузок и записи проверок в PostgreSQL.
- Live REST: собственная история, сохранение результата, инвалидирование/очистка,
  атомарный захват и завершение стадий отправки, адрес собственного наставника.
- `TeamData` и `BackendData`: методы `equator_history`, `equator_save`, `equator_invalidate`,
  `equator_clear`, `equator_claim`, `equator_delivery`, `mentor_chat`.
- Срок задаётся `H4_HISTORY_TTL_DAYS` (по умолчанию 7); backend проверяет конфигурацию при старте.
- Backend задаёт идентичность и время записи самостоятельно. Переданные клиентом created_at/expires_at
  не определяют срок хранения; повтор сохранения не продлевает срок.
- После новой загрузки поколение меняется до чтения файла. Поздний результат старого поколения
  сохраняется неактуальным и не получает рабочую кнопку отправки.
- Результат проверки после создания неизменяем. Разрешено только однократно дополнить пустой
  Telegram file_id; повтор не заменяет отчёт, вердикт и уже прикреплённый файл.
- Состояния file/report хранятся отдельно. Захват выполняется под транзакционной блокировкой
  пользователя; повторный/конкурентный захват получает conflict. `unknown` требует явного
  `retry_unknown`; `sending` не допускает конкурентного захвата.
- Чат разрешается только для собственного наставника той же команды. Это служебный REST;
  инструмент записи в корпоративные сервисы не добавлен.
- OpenAPI обновлён; добавлено описание необязательного `BriefItem.render_text` для соседней правки H0.

## Проверки

Go отсутствует в PATH Windows, поэтому проверки выполнены в локальном образе `golang:1.24-alpine`.
Тесты использовали отдельный одноразовый `pgvector/pgvector:pg16`, без данных рабочего приложения.
Корень репозитория монтировался в `/repo`, рабочий каталог — `/repo/backend`.

Команды внутри контейнера:

```text
gofmt -w <изменённые Go-файлы H4 и brief_render>

go vet ./...
go test ./internal/store -run TestFR_H4 -count=1
go tool cover -func=coverage.out
```

Все перечисленные проверки прошли. Полный backend: **91,1 %** покрытия statements (1599/1755).
По пакетам: cmd/backend 81,7 %, api 99,1 %, auth 100 %, mcp 100 %, server 88,9 %, store 89,0 %.
Миграции не содержат исполняемого Go-кода. Профиль — `backend/coverage.out`.

Покрыты история/изоляция, поздний результат старого поколения, очистка истёкшей записи,
сохранение отчёта при повторе, однократное прикрепление file_id, конкурентный захват стадии,

передача явного повтора неизвестного исхода и распространение conflict.
Ruff для изменённых модулей клиента и этих тестов прошёл.
OpenAPI разобран PyYAML, все внутренние `$ref` разрешаются.
`openspec validate h4-history-rest` прошёл.

Первый пробный Go-прогон без PostgreSQL имел один инфраструктурный сбой: был смонтирован только

## Ограничения и дальнейшие действия

- Истёкшая запись сразу недоступна для действий и сравнения. Физическая очистка выполняется при
  обращениях к H4; если требуется удалять данные и при полном отсутствии активности, добавить
  периодический cleanup backend/SQL job и тест времени удаления.
- Состояние `sending` после аварии не доказывает ни доставку, ни её отсутствие. Для надёжной
  эксплуатации нескольких агентов требуется lease/worker token и процедура восстановления;
  нельзя автоматически пересылать потенциально доставленную часть.
- Конфигурация backend и агента ограничивает TTL диапазоном 1–36500 дней;
  одинаковая валидация добавлена при интеграции основным агентом.
- Адрес наставника будет null до его привязки к Telegram. Бот должен показывать «не доставлено»,
  сохраняя отдельную отметку проверки.
- Покрытие выше относится к Go statements; реальные внешние Jira/Telegram и настоящая LLM
  не вызываются backend-тестами. Общую пользовательскую приёмку выполняет основной агент.
