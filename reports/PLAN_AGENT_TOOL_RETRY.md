# План: повтор шага агента с `tool_choice: "required"` и проверка фактов о людях

**Статус:** план, код не менялся. **Дата:** 13.11. **Ветка:** `feat/agent-orchestrator`.
**Связано:** `reports/BUG_AGENT_ANSWERS_FROM_HISTORY.md`, `reports/REPORT_HISTORY_FACTS_AND_TELEGRAM_CITATIONS.md`.

## Зачем

После исправления 13.11 ответ без инструментов с ключом задачи или номером PR отклоняется и уходит в Router. Осталось две проблемы:

1. **Имена и роли из карточки команды кодом не проверяются.** «Твой наставник — Анна» из истории проходит без инструмента и без ссылки (сценарий из Studio).
2. **Отказ сразу отдаёт запрос Router.** Модель ничего не выдумала, она просто не вызвала инструмент. Ответ исполнителя вместо живого ответа агента — лишняя потеря качества.

Цель: если модель ответила фактом без инструмента, она получает **одну** попытку вызвать инструмент. Если не вышло, работает прежний запасной путь (Router).

## Проверка `tool_choice: "required"` (сделана 13.11)

- OpenRouter заявляет `tool_choice` для `deepseek/deepseek-v4.1-flash-1017`.
- 4 живых запроса с `provider.require_parameters: true`:

| Вопрос | Без `tool_choice` | С `"required"` |
|---|---|---|
| «Привет!» | без инструментов, текст | `team_q3`, `brief_now`, текста нет |
| «Как лучше начать первый день?» | 5 инструментов + текст | 4 инструмента, текста нет |

- Провайдеры разные (Wafer, Cohere, StepFun, Relace); все приняли параметр.
- Вывод: параметр работает. Он заставляет вызвать инструмент, но не выбирает удачный: на «Привет!» вызваны лишние. Поэтому `required` — только на повторном шаге после отказа, не на первом.

## Как работает после изменений

```
шаг 1: модель отвечает без инструментов
  └─ verify: факт без инструмента? (ключ задачи, PR, имя в роли из карточки)
       ├─ нет  → ответ показывается (как сейчас)
       └─ да   → Rejected("no_tool")
            └─ шаг 2: служебное сообщение + tool_choice="required"
                 └─ инструменты выполняются, результаты с метками S#
                      └─ шаг 3: обычный шаг (без required), ответ с [S#] → verify → ссылки
            └─ любой сбой на шагах 2–3 → FR-AG-05: Router → Executor
```

Шагов не больше `MAX_STEPS = 3`: повтор возможен только если на шаге 1 не было инструментов. Повтор — максимум один за ход.

## Изменения по файлам

### 1. `agent/buddy/llm/client.py`
- `CompatibleLLM.chat(messages, tools, tool_choice: str | None = None)`.
- Если `tool_choice` передан: добавить в тело `"tool_choice": tool_choice` и `"provider": {..., "require_parameters": True}`, чтобы OpenRouter не отправил запрос провайдеру, который параметр молча игнорирует.
- Без `tool_choice` тело запроса не меняется.
- Тот же аргумент — в первый `chat` в файле (строка ~29) и во `FakeLLM`: фейк записывает полученный `tool_choice`, чтобы тесты могли его проверить.

### 2. `agent/buddy/agent/loop.py`
- Новая причина отказа `Rejected("no_tool")`: в ходе не было инструментов, а в ответе есть факт. Сейчас это `task` и `pr` при пустом `observed`; добавить отдельную причину, чтобы отличать её от «выдуманного» факта.
- **Узкая проверка имён:** на ходе без инструментов загрузить карточку (`runtime.data.team_card(context.user_id)`, без LLM) и отклонять ответ, где имя человека из `people[].name` стоит рядом со словом роли: «наставник», «тимлид», «первый контакт», «отвечает за», «ментор». «Спроси у Анны» проходит, «твой наставник — Анна» — нет. Ошибка чтения карточки → проверка имён пропускается (не ломает ход).
- **Повтор:** в `Agent.answer`, если `verify` бросил `no_tool` и повтора ещё не было:
  - добавить в `messages` ответ модели как `assistant` и служебное `user`-сообщение: «В этом ходу ты не вызвал инструменты, а ответ содержит факты. Вызови нужный инструмент; ответ из истории не подходит.»;
  - следующий `llm.chat(..., tool_choice="required")`;
  - дальше обычный цикл: инструменты → шаг без `required` → `verify` → `_compose`.
- Все остальные причины (`answer`, `label`, `task`/`pr` при выполненных инструментах, `budget`, `steps`, таймаут, ошибка LLM) — сразу запасной путь, как сейчас.
- Лог: `agent retry: no_tool` (только причина, без текста пользователя и модели — как сейчас для `agent fallback`).
- Ответ модели с шага 1 пользователю не показывается и в память не пишется.

### 3. `agent/buddy/llm/trace.py` / LangGraph Studio

## Риски

| Риск | Что будет | Как смягчить |
|---|---|---|
| Провайдер не поддерживает `tool_choice` | запрос падает → Router | `require_parameters: true`; запасной путь уже есть |
| `required` вызывает лишние инструменты | лишние секунды, лишние ссылки | только на повторе, бюджет `MAX_CALLS = 4` уже ограничивает |
| Узкая проверка имён пропустит «Анна — твой наставник» в другой формулировке | факт без ссылки | список слов роли вынести в константу, расширять по eval |
| Ложный отказ на совете с именем и словом роли («наставник Анна подскажет») | повтор → инструмент → ответ с фактом и ссылкой | приемлемо: ответ становится точнее |
| Сменится модель (`LLM_MODEL`) | поддержка `tool_choice` может отличаться | проверять в `evals/run_agent.py` перед сменой |

## Что согласовать с Даниилом

1. **FR-AG-05 меняется.** Сейчас «нарушение FR-AG-09 → сразу запасной вариант». Предлагаем исключение: для отказа «факт без инструмента» — одна повторная попытка с обязательным вызовом инструмента. Ответ модели с первой попытки по-прежнему не показывается.
2. **FR-AG-09 расширяется** на имена людей из карточки в утверждениях о роли. Согласовать список слов роли и то, что «спроси у Анны» считается советом, а не фактом.
3. **История — не источник фактов** (п. 1г `proposal.md`, уже реализовано промптом и проверкой PR/ключей): подтвердить формулировку в FR-MEM-04.
4. **Цена и задержка:** +1–2 запроса и +2–4 с на ходах с повтором. Подтвердить, что это приемлемо для бюджета пилота.
5. **`require_parameters: true` для OpenRouter** сужает выбор провайдеров на повторном шаге. Подтвердить, что это допустимо вместе с `data_collection: deny`.
6. **Память по профилю, а не по треду** (п. 1д `proposal.md`): оставить как есть или ограничить историю тредом/чатом. От решения зависит, как часто будет срабатывать повтор.
7. **Новые eval-кейсы** в `evals/agent/cases.jsonl` (зона Даниила): два кейса из раздела 6.
