## 3. Найденные пробелы

### Обязательные проверки

1. `title_markers` / `structure` принимают три из четырёх косвенных признаков титула;
   имя стажёра не проверяется. Заголовок раздела достаточен даже без содержимого.
2. `judge` принимает пустой объект Jira `{}` как существующую задачу с результатом `ok`,
   если на слайде нет распознанного статуса. В сочетании с пустыми разделами возможен ложный допуск.
3. `mentions` присваивает один первый статус всем ключам строки.
   В строке «ORD-2 сделано, теперь в работе ORD-3» обе задачи получают `done`.
   Существующий тест закрепляет именно это поведение; менять нужно и правило, и тест.
4. Ссылка Jira берётся из `issue.url` без проверки безопасности и конкретности объекта.
   Путь загрузки H4 обходит `graph.guarded`, поэтому общая проверка графа его не защищает.
5. Любой `RemoteToolError` трактуется как «задача не найдена». В Hub он означает общий `isError`,
   без классификации причины: ошибка прав или сервиса может быть показана неверно.
6. В пути H4 не найдено ограничения Jira-ключей проектами команды. `Hub.call` использует `user_id`
   для аудита, но сам не ограничивает Jira-проект. Нужна проверка контекста до чтения чужой задачи.

Пункты 1–4 проверены отдельными локальными вызовами функций. Пункты 5–6 установлены по коду;
реальные Jira-аккаунты в этом исследовании не проверялись.

### Версии и отправка

- `Check` хранит только итоговый текст, ссылки, passed и file_id; структурированного результата нет.
- `EquatorService.checks` — словарь процесса без постоянного хранения и ограничения размера.
- ID основан на содержимом файла и user_id: повтор файла перезаписывает запись вместо отдельной попытки.
- Отправка любой ранее успешной записи остаётся доступной после загрузки новой неуспешной версии.
- `mark_progress` выполняется до доставки наставнику. Доставку нельзя определить по этой отметке.
- Повторная отметка трекера идемпотентна, но пересылка файла/отчёта при повторном callback — нет.
- Ошибки отправки файла или отчёта не оформлены в отдельные состояния и безопасный повтор.
- Адрес наставника берётся из `AgentService.chats` в памяти: после рестарта наставник должен снова написать.
- H4 не представлен в `/help`, инструментах текстового агента и его памяти. Отправить файл можно,
  но текстовый вопрос «как проверить презентацию?» не имеет надёжного отдельного сценария без LLM.
- Отчёт по большому числу задач может превысить лимит Telegram. HTML не разбивается на сообщения;
  plain fallback может обрезать замечания.

### Шаг 6. Исправить формат «Ещё N»

Ответственный: Эмиль. Файлы: `brief/service.py`, `brief/models.py`, при необходимости `bot/stage_two.py`.

Причина скриншота:

- `BriefService.now_brief` вызывает `_wording(shown, main)` только для первых пяти пунктов.
- `signal("more")` вызывает `item.line()` напрямую для скрытых пунктов.
- `BriefItem.line()` добавляет `CLASS_ICON`; LLM при переформулировке первых пяти их убирает.
- Число 3 корректно: в учебном брифе 8 изменений, лимит 5. Сноски `[1]`–`[3]` во втором сообщении
  также корректны: их нумерация локальна сообщению, а номера пунктов продолжаются с 6.

Изменения:

1. Общая функция форматирования пунктов для обоих сообщений: номер, источник, краткий текст,
   ссылка-сноска; без цветного кружка. Заголовок продолжения может оставаться «Остальные изменения».
2. Код отвечает за структуру строки и источник; LLM переформулирует только содержимое.
   Один стиль действует при частичном ответе модели и полностью шаблонном fallback.
3. Скрытые пункты при первом открытии пропускать через ту же `_wording`, результат сохранять
   в черновике/хранилище, чтобы повторное нажатие не меняло текст и не вызывало LLM снова.
   После рестарта можно восстановить формат из исходных пунктов; для неизменности формулировок
   сохранять проверенные тексты вместе с брифом либо отдельным постоянным кэшем.
4. Сохранить нумерацию 6…N, порядок, URL и redirect-токены по item_id, событие прочтения,
   поведение оценок и ровно первые пять пунктов в исходном сообщении.
5. Проверить `/brief`, расписание, «что нового?» в режиме агента и шаблонный режим:
   свободный финальный ответ агента может повторно переформулировать бриф.
   Для одиночного брифа зафиксировать передачу готового формата, для составного ответа
   не потерять другие части вопроса пользователя.

Готово: первые пять пунктов и «Ещё 3» имеют одинаковую структуру с LLM и без неё,
без потери ссылок, порядка, кнопок и метрик.

### Шаг 7. Приёмка и небольшие коммиты

- На каждый новый/изменённый Scenario — тест с ID требования.
- Регрессии H4: пустые разделы; каждое поле титула; отсутствующий/непонятный/смешанный статус;
  два ключа с разными статусами; пустой ответ Jira; неверный URL; чужой проект; 401/403/404/timeout;
  неизвестный ключ демо; частично нечитаемые слайды; длинный отчёт.
- Версии: первая/повторная/исправленная/ухудшенная; смена номера слайда; смена Jira без правки файла;
  рестарт; чужие IDs; разные демо-владельцы; сброс; конкурентные загрузки и нажатия.
- Отправка: нет наставника/чата; файл отправился, отчёт нет; повтор; сбой трекера;
  устаревшая кнопка; сохранённое первое completed_at.
- Рекомендации: schema/timeout/injection/неизвестный слайд; границы настроенных лимитов
  (по умолчанию 10/11 слайдов и 100/101 слово), изменение обоих параметров через env,
  отклонение нуля, отрицательных и нецелых значений;
  предупреждение не блокирует допуск.
- Бриф: 0/5/8 изменений, частичный/плохой ответ LLM, повтор «Ещё», рестарт,
  нумерация, ссылки, feedback и read-event.
- Полный pytest с покрытием agent >80%; ruff; OpenSpec. При backend-изменениях — Go-тесты,
  интеграция с PostgreSQL и покрытие backend >80%. Обновление генерируемых seed/fixtures
  выполнять генераторами; отдельно проверить пакет `agent/buddy/demo/data`.
- Evals H4 с настоящей LLM запускать на синтетических презентациях: соответствие замечаний слайдам,
  пропуски, выдуманные замечания, доля fallback, время. Базовый сценарий обязан работать без модели.
- Telegram/Compose-приёмка — после отдельного поручения на запуск бота. Для проверки PowerPoint-MCP
  поднимать только нужный сервис; `make pptx-up` может запустить весь стек вместе с агентом.
- После приёмки обновить отчёт, согласованные документы и архивировать OpenSpec; не смешивать
  изменения H4 с незакоммиченной трассировкой.

Предлагаемые коммиты: согласованные спецификации → обязательные проверки → хранение версий →
сравнение → рекомендации → доставка/UI → формат брифа → результаты приёмки.
Сообщения коммитов на английском.

## 5. Что ещё уточнить у команды

Эти пункты не отменяют согласованные правила, но влияют на реализацию:

1. **Даниил:** есть ли новые учебные презентации вне локальной ветки? Спецификация уже
   согласована Эмилем и опубликована; новые примеры нужно сверять с ней.
2. **Илья + Эмиль:** подтвердить контракт хранения live-истории и получения адреса наставника;
   выбрать локальное постоянное хранилище демо. Срок хранения согласован: настраиваемый,
   по умолчанию 7 дней. Предложенная семантика сбросов — в шаге 3.
3. **Решено Эмилем:** титул сверяется с доверенным профилем/карточкой без обязательного
   слова «Имя» перед ФИО; неоднозначность объясняется в отчёте.
4. **Команда:** какие реальные Jira-статусы и проекты нужны для live-приёмки? Без аккаунтов
   можно принять демо и контрактные тесты, но нельзя заявлять проверенную live-интеграцию.
5. **Даниил:** §10.5 предлагает проверить презентацию самого хакатона. Обычно в ней нет шести
   разделов стажировки и ключей ORD. Нужно либо честно показать замечания H4, либо подготовить
   отдельную учебную презентацию стажёра; не ослаблять обязательные критерии ради демонстрации.

Напоминание об экваторе относится к §10.3 H0, а не к полному §10.5 H4. Пока предлагается отдельной
задачей: в текущем профиле есть internship_week, но нет согласованной точной даты экватора;
вычислять «через N дней» из номера недели нельзя.
