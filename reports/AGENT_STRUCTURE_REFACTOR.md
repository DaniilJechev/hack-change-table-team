# Рефакторинг структуры агента: было → стало

Дата: 15 ноября 2026. Ветка: `improved_structure`.

## Результат

Управление запросом собрано в `orchestration/`; Telegram разделён по видам
обработчиков. Каталог сценариев стал общим источником имён, параметров, ролей,
описаний LLM-инструментов и выбора обработчика. Продуктовые пакеты H0–H4 сохранены.
Подробная новая структура и схемы выполнения находятся в [agent/README.md](../agent/README.md).

## Каталог: границы ответственности

Каталог содержит 16 маршрутизируемых сценариев и два фоновых триггера. Запись
задаёт разрешённые параметры, роли, описание, адаптер и доступность агентному циклу.
Схема RouteDecision и параметры Router получаются из того же набора записей.
Registry проверяет роль перед обращением к продуктовому сервису.

Валидация аргументов сохраняет прежние границы: дополнительные поля и идентификаторы
пользователя не разрешены, параметры публичных инструментов строковые. Обязательность
параметров не ужесточалась, чтобы сохранить существующие уточнения. ID продолжения
диалога не попадают в публичную схему инструментов модели.

MCP-политики остаются в `mcp_hub/policy.py`. Каталог не заменяет проверки Hub,
не разрешает произвольные инструменты и не подменяет доверенный пользовательский Context.
H4 запускается загрузкой файла; подача заявки и другие действия кнопок не открыты
модели автоматически.

## Совместимость и сохранённые ограничения

- Старые пути импортов сохранены тонкими модулями совместимости; реализации не дублируются.
- Исторические имена логгеров агентного цикла и графа сохранены: их используют evals и проверки трасс.
- Настройки engine/mode, режим demo, фикстуры и запасные пути без LLM сохранены.
- Telegram и клиентский HTTP API продолжают использовать прежние поля ответов и callback-строки.
- `ScenarioResult` отделяет содержимое ответа, но сервисы пока могут создавать готовые действия.
  Полная замена их семантическими командами интерфейса — отдельная миграция двух каналов.
- `AgentService` остаётся фасадом интерактивных операций; это не полное устранение
  координации из класса. Сборка продуктовых зависимостей, состояние и выполнение
  сценариев получили отдельные компоненты.
- `rag/` оставлен с прежним именем: это допустимый вариант исходного предложения;
  путь индекса и команды ingestion не менялись.
- Получатели фоновых проверок и связь сообщения с брифом по-прежнему теряются
  при перезапуске. Это прямо зафиксировано в продукте, §10.3; добавление постоянного
  хранилища изменило бы согласованное поведение и потребовало отдельного OpenSpec.
- Старые тексты автономного каркаса сохранены для совместимости его режима и тестов;
  актуальное описание реализации вынесено в README и метаданные пакета.

Изменений продуктовых требований нет. `docs/` и `openspec/specs/` не редактировались;
новая поведенческая дельта OpenSpec для переносов модулей не создавалась.

| OpenSpec | **35 passed, 0 failed**; существующие предупреждения о длинных требованиях и архивировании дельт |
| Проверка whitespace diff | Пройдена |
| Backend в Docker | Все пакеты прошли `go test ./... -count=1`, включая интеграции с PostgreSQL |
| Покрытие backend | **90,2 %** statements; каждый тестируемый пакет выше 80 % |

Добавлены девять регрессионных проверок: совпадение каталога со схемой Router,
отсутствие identity/internal полей в инструментах, наборы инструментов по ролям,
запрет наставнического обработчика до его вызова, выполнение фонового триггера
на внедрённом сервисе, проекция содержимого ответа и четыре проверки совместимости импортов.

Первый прогон исходного состояния: 812 тестов прошли, 48 не смогли создать
временные файлы из-за ограничений Windows. Для итогового прогона временная папка
и pytest cache перенесены внутрь рабочего каталога. При проверке рефакторинга
обнаружена и исправлена регрессия имени логгера, мешавшая evals учитывать сетевые ошибки.

Go запускался в `golang:1.24-alpine`, PostgreSQL — в `pgvector/pgvector:pg16`.
Проверка использовала отдельную временную Docker-сеть и контейнер БД без публикации
порта на хост. По завершении контейнер и сеть удалены; Docker Desktop оставлен запущенным.

Бот не запускался. Реальные LLM и корпоративные аккаунты не использовались.
Изначально существовавшие `.presentation-draft/`, `output/` и
`reports/EVALUATOR_HANDOFF.md` не изменялись.

## Рекомендуемый порядок ревью

1. `catalog.py` и `registry.py`: состав сценариев, роли и выбор обработчиков.
2. `contracts.py`, `presentation.py`, `bot/rendering.py`: совместимость ответов.
3. `orchestration/graph.py`, `agent_loop.py`: сохранение исполнения и запасных путей.
4. `bot/registration.py` и разделённые обработчики: порядок регистрации и доставка.
5. `bootstrap.py`, `scheduler/jobs.py`, `observability/`: перенос обязанностей.
6. README и новые регрессионные тесты.
