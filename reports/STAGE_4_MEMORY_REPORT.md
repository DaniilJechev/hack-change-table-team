# Этап 4: движок LangGraph, контекстная память, доработка H0 и H3

Дата: 11 ноября 2026. Ветка `feat/stage-4-langgraph`, OpenSpec-изменение `stage-4-langgraph-memory`.
Приёмка, как и раньше, — на синтетических фикстурах в демо-режиме: без реальной LLM, без API-ключа и без внешних аккаунтов.

## Итог в двух словах

Бот теперь помнит последние 6 ходов диалога (30 минут) и понимает короткие уточнения: «подробнее про 2-й пункт», «что с PR #45?», «а по календарю?», «а кто за неё отвечает?», «подробнее», «а для ORD-120?», «ещё». Обработка запроса идёт через детерминированный граф LangGraph; поведение без уточнений совпадает с прежним движком один в один. В живом режиме память хранится в Redis из Compose (согласовано с Ильёй), в демо — в памяти процесса.

## Что сделано

| Требование | Реализация | Где |
|---|---|---|
| ST4-GRAPH-1 граф | `load_memory → resolve_followup → route → brief\|playbook\|team\|access\|template → guard → save_memory`; ребро выбирает код по кейсу, исполнители вызывают прежние сервисы | `agent/buddy/graph/` |

### Stage 2 — контекстная память
| Требование | Реализация | Где |
|---|---|---|
| FR-MEM-01 окно | 6 ходов: кейс, параметры, сущности (задача Jira, PR, человек, `brief`, `brief_items`, `chunks`), краткий итог; TTL 30 минут | `memory/store.py` |
| FR-MEM-02 изоляция | Ключ только из доверенного профиля: `live:<team_id>:<user_id>`, в демо — с номером сессии; ходы другой роли не используются | `memory/store.py` |
| FR-MEM-03 очистка | `/reset`; `/demo reset\|off\|mentor\|intern`; смена команды или роли | `bot/stage_two.py`, `service.py` |
| FR-MEM-04 данные, не инструкции | Сырые сообщения и ответы LLM не хранятся; токены (`ghp_…`, `sk-…`, JWT, Bearer, длинные ключи) вырезаются; сущности — только ID по белому шаблону; в LLM память уходит как JSON | `memory/store.py` |
| FR-MEM-05 уточнения | Правила без LLM; переформулировка LLM — только в живом режиме, только для фраз, похожих на уточнение, ответ проверяется схемой `{"question"}`, при ошибке — правила | `memory/followup.py` |
| FR-MEM-06 хранилище | Демо и тесты — процесс; живой режим — Redis (`RPUSH` + `LTRIM` до 6 + `EXPIRE` 1800 с), ключ `buddy:memory:live:…`; Redis недоступен → ответ без памяти и предупреждение в журнале; `MEMORY_ENABLED=false` отключает память | `memory/store.py`, `app.py`, `docker-compose.yml` |

### Stage 3 — H0, уточнения по брифу (FR-H0-12)
- Ответ брифа сохраняет в памяти `brief_id`, ID пунктов в порядке показа (включая скрытые под «Ещё N»), номера PR и ключи задач.
- «подробнее про N-й пункт» / «второй пункт» → `BriefService.item`: пункт из сохранённого брифа этого пользователя, ссылка подставляется кодом по `item_id` (с токенами редиректа, если включены).
- «что с PR #45?» → все пункты брифа по этому PR.
- «подробнее про 9-й пункт» при 5+3 пунктах → «В последнем брифе нет пункта 9.» без ссылок.
- «а по календарю?» после брифа → бриф только по календарю (прежняя логика FR-H0-07).
- Если брифа с пунктами в памяти нет («Изменений нет»), «подробнее про 2-й пункт» показывает обычный бриф.

### Stage 4 — H3, уточнения по playbook (FR-H3-07)
- Ответ сохраняет `chunk_id` показанных фрагментов.
- Уточнение с местоимением («а кто за неё отвечает?») → поиск по «прошлый вопрос + уточнение», ссылка на `development-principles.md` сохраняется.
- «подробнее» / «ещё» → `PlaybookService.details`: те же фрагменты по `chunk_id` без нового поиска; с LLM — до 8 предложений, без LLM — фрагменты с длинными выдержками (до 900 символов).
- Проверка опоры для `answer` и `details`: ответ LLM принимается, только если ≥ 2 его основ слов и ≥ 35 % его уникальных основ есть во фрагментах. Иначе показываются фрагменты со ссылками.
- «а пароль от Wi-Fi?» после ответа по playbook → «В playbook этого нет» + [Спросить наставника].

### Stage 5 — Router
- RT-08: Router получает сводку прошлого хода (кейс + сущности, без текста сообщений) отдельным JSON-полем. Если модель для стажёра предлагает `interns_status`, ответ модели отбрасывается и работают правила.
- RT-09: границы `team_q5`/`brief_now`, `team_q8`/`playbook_qa`, `interns_status`/`access_status`, `team_q2`/`team_q1` в промпте; нормализация в коде: `situation` — нижний регистр, ключ Jira — верхний (на всех путях Router).

## Как делали

Ядро (память, граф, сервис, Router RT-08, спецификация под Redis) писалось в основной сессии. Параллельно работали четыре агента с непересекающимися файлами: Router RT-09, уточнения H0, уточнения H3, набор evals памяти. Каждый отчитался тестами; результаты перепроверены общим прогоном на обоих движках.

## Отступления и решения

1. **FR-MEM-06: Redis вместо REST backend.** Илья согласовал Redis; новых эндпоинтов не нужно. В Compose агенту добавлены `REDIS_URL`, `AGENT_ENGINE`, `MEMORY_ENABLED` и зависимость от `redis` (зона Ильи — просьба посмотреть).
2. **LangGraph-checkpointer не используется.** Окно, TTL и изоляция — своя тонкая обёртка над Redis/словарём: проще проверить правила FR-MEM-02/04 и не хранить в Redis состояние графа с объектами runtime.
3. **Параметры уточнений** (`brief_id`, `item`, `pr`, `chunks`) создаёт только код из памяти; из ответа LLM Router они не принимаются (белый список параметров не расширен).
4. **Уточнение «а …» без местоимения** («а пароль от Wi-Fi?») не склеивается с прошлым вопросом, иначе BM25 нашёл бы прошлую тему вместо отказа.

## Что не сделано и что не проверено

- **Реальная LLM.** Ни переформулировка уточнений, ни новый промпт Router, ни проверка опоры на настоящих ответах модели не запускались — ключ не использовался без разрешения. Следующий шаг: `evals/run_llm_compare.py` с Haiku 5.5 по Router и прогон evals памяти с LLM.
- **Живой Redis.** `RedisStore` проверен на подставном клиенте; с настоящим Redis в Compose не запускался (бот выключен).
- **«подробнее» в H3 без LLM** показывает те же фрагменты, если они короткие: полноценный развёрнутый ответ возможен только с LLM.
- **ORD-120/ORD-121 в H1.** Фикстуры Jira есть только для ORD-118, поэтому уточнение «а для ORD-120?» в демо маршрутизируется верно, но отвечает «Не удалось получить задачу». В демо-протокол не включено.
- **`openspec validate`** не запускался: нужен Node ≥ 22.12, локально 20.
- **Docker-образ** не пересобирался (зависимости langgraph и redis берутся из lock-файла).
