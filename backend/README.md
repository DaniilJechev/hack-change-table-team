# Backend · Этапы 1–2

Go 1.24, net/http, pgx v5 через database/sql, миграции goose. При запуске применяются
встроенные SQL-миграции; ошибка БД/миграции останавливает процесс без вывода DSN.
`GET /health` сохраняет контракт Этапа 0. `GET /ready` проверяет БД.

## Локальные пользователи и приглашения

```text
make up
make seed
make invite USER_ID=demo-daniil TTL=24h
```

Seed берётся из существующего `seed/users.yaml`. Импорт повторяемый, атомарный,
не сбрасывает привязки и коды. Перенос существующего пользователя в другую команду
запрещён; изменение требует отдельной миграции. Роли: intern, mentor, teamlead.
Перед фиксацией проверяются все сохранённые связи с наставниками. Частичный seed
не может сменить роль наставника, если на него ещё ссылаются пользователи;
такой импорт откатывается целиком. Если связи сняты тем же импортом, смена роли разрешена.
Приглашение выдаётся только непривязанному пользователю, действует 24 часа по
умолчанию (не более 7 суток). Команда выводит код один раз; передать его сотруднику
для `/start <код>`, не записывать в репозиторий или журналы.

## REST для Эмиля

Машиночитаемая схема — [openapi.yaml](openapi.yaml).

`BACKEND_URL` и `BUDDY_SERVICE_KEY` уже переданы агенту через Compose.
Каждый `/api/v1/*` требует заголовок `X-Buddy-Key: <BUDDY_SERVICE_KEY>`.
В локальном Compose ключ по умолчанию демонстрационный `buddy_local_demo`;
для реального использования задать собственный ключ в `.env`. Пустой ключ при
запуске бинарника запрещён. REST доступен на host только через loopback.

| Запрос | Тело / ответ |
|---|---|
| `POST /api/v1/auth/bind` | `{"code":"…","telegram_user_id":123,"telegram_chat_id":123}` |
| `GET /api/v1/auth/telegram/123` | Профиль привязанного пользователя |

Успешный ответ: `{"user_id":"demo-daniil","display_name":"Даниил","role":"intern","team_id":"demo-orders","mentor_id":"demo-anna"}`.
Роль, команда и наставник берутся только из БД. Привязка разрешена только в личном
чате (положительные и одинаковые Telegram user/chat ID); повторный код не работает.
Коды хранятся как SHA-256; транзакция и блокировки защищают от одновременного
погашения. Конфликт не меняет прежнюю привязку и не расходует приглашение.

Ошибки имеют вид `{"error":{"code":"invalid_invitation","message":"Код не подошёл, спроси наставника"}}`:

| HTTP | code | Причина |
|---|---|---|
| 400 | invalid_request | Некорректный JSON, неизвестные поля, тело >4 KiB, не личный чат |
| 400 | invalid_invitation | Код неизвестен, истёк или уже использован |
| 401 | unauthorized | Неверный служебный ключ |
| 404 | not_found | Telegram ID не привязан |
| 409 | binding_conflict | Telegram/сотрудник уже связан |
| 503 | unavailable | БД недоступна |

Telegram-обработчик `/start` уже подключён к REST в main: ID берутся из
`message.from_user.id` и `message.chat.id`, а профиль — из ответа backend.
Прикладные маршруты и MCP Этапа 2 описаны ниже.

## Проверки

`make test` и `make cover` запускают Go-тесты с отдельным временным PostgreSQL
в Docker. Если задан `TEST_DATABASE_URL`, используется эта БД с отдельными схемами
для каждого теста; таблицы разработчика не затрагиваются. CI задаёт отдельный
PostgreSQL service. `GO_RACE=1 make cover` включает race detector.
`make test-backend-integration` — только Go и PostgreSQL.

Запуск вне Docker: переменные `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`,
`PGPASSWORD`, `PGSSLMODE` или `DATABASE_URL`, плюс `BUDDY_SERVICE_KEY`.
`SEED_USERS_PATH` задаёт путь seed для `backend seed` (в Compose `/seed/users.yaml`).

## Этап 2: buddy-mcp и наши данные

`/mcp` — настоящий Streamable HTTP на [официальном MCP Go SDK](https://github.com/modelcontextprotocol/go-sdk),
закреплённом на v1.3.1 для совместимости с Go 1.24. JSON-ответы, stateless transport:
сервер не сохраняет права пользователя в MCP-сессии. `initialize`, `tools/list` и каждый
`tools/call` требуют **оба** заголовка `X-Buddy-Key` и `X-Buddy-User`.
Профиль, роль и команда перечитываются из PostgreSQL на каждом HTTP-запросе;
роль и team_id в аргументах инструментов не принимаются. Таймаут запроса — 5 секунд,
максимальное тело — 1 MiB. Ошибки БД/секреты не передаются клиенту.

| MCP-инструмент | Аргументы | Результат |
|---|---|---|
| `user_profile_get` | `{}` | Свой профиль, `teamlead_id`, `logins`, `internship_week` |
| `team_card_get` | `{"section":"people"}` или `{}` | `team_id`, `version`, `document`, `source_path` |
| `team_faq_search` | `{"text":"Kafka"}` | `items`: до 20 опубликованных ответов своей команды |
| `access_catalog_get` | `{"objects":["repo"]}` или `{}` | `items`: объекты своей команды для своей роли |
| `access_marks_get` | `{}` | `items`: свои `object_id`, `requested_at` |
| `interns_list` | `{}` | `items`: профили стажёров и `snapshot` (либо null) |

Все инструменты имеют `readOnlyHint=true`. `interns_list` доступен наставнику
(только его стажёры) и тимлиду (стажёры своей команды). Неизвестные аргументы,
включая чужую команду или пользователя, отклоняются схемой SDK.
Неизвестный пользователь/неверный ключ — HTTP 401; ошибка внутри инструмента — MCP
`isError=true` с безопасным русским текстом. При отсутствии карточки — «Данные не найдены».
Пустые наборы возвращаются как `items: []`. Неделя стажировки — null, если дата неизвестна;
фиктивные логины и даты не подставляются.

### REST-контракты

Все новые маршруты требуют те же два заголовка. Поля пользователя, команды,
автора ответа и серверного времени вычисляются сервером; лишние поля отклоняются.
Существующие `/api/v1/auth/*` по-прежнему требуют только служебный ключ.
Точные схемы запросов и ответов — [openapi.yaml](openapi.yaml).

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/profile` | Свой расширенный профиль |
| `GET /api/v1/team-card?section=people&version=1` | Своя карточка, необязательные раздел и версия |
| `GET /api/v1/access-catalog?object=repo` | Каталог; `object` можно повторить |
| `PUT /api/v1/access-marks/{object}` | «Я запросил», **пустое тело** |
| `GET /api/v1/access-marks` | Свои отметки |
| `POST /api/v1/access-snapshots` | `{"id":"s1","objects":[{"object_id":"repo","status":"missing"}]}` |
| `GET /api/v1/access-snapshots/latest` | Последний свой снимок |
| `GET /api/v1/interns` | Те же права и данные, что у `interns_list` |
| `POST /api/v1/briefs` | `{"id":"b1","items":[]}` — новый draft |
| `GET /api/v1/briefs/{id}` | Свой бриф |
| `PATCH /api/v1/briefs/{id}` | `{"status":"sent"}` или `{"status":"failed"}` |
| `POST /api/v1/briefs/{id}/events` | `{"id":"e1","kind":"read"}`; click требует `item_id` |
| `POST /api/v1/questions` | `{"id":"q1","text":"Зачем Kafka?","assigned_to":"demo-anna"}` |
| `GET /api/v1/questions/{id}` | Доступен создателю вопроса и назначенному адресату |
| `POST /api/v1/questions/{id}/answer` | `{"text":"Ответ человека"}`, только назначенный адресат |
| `PATCH /api/v1/questions/{id}` | `{"helpful":true}`, только создатель вопроса с ответом |
| `POST /api/v1/faq` | `{"id":"f1","question_id":"q1","consent":true}`, только автор ответа |
| `GET /api/v1/faq/{id}` | Опубликованный FAQ своей команды |
| `GET /api/v1/faq?text=Kafka` | Буквальная подстрока в вопросе или ответе, без LLM |

ID записей задаёт агент: 1–128 ASCII-символов, первый буквенно-цифровой, далее
буквы/цифры и `._:-`. Повтор с тем же ID и содержимым возвращает прежнюю запись;
другое содержимое — 409 `conflict`. `PUT access-marks` возвращает первоначальную дату;
отметить неизвестный, скрытый для роли или запрещённый объект нельзя (404).
В снимке принимаются только объекты своей команды/роли без повторов. Поле `error`
предназначено для короткого безопасного кода ошибки проверки, до 256 байт;
агент должен сохранять предыдущий известный статус при недоступном инструменте.
Последний снимок определяется порядком вставки, повтор старого ID его не меняет.

Бриф хранит все нормализованные пункты (до 100); выбор пяти для сообщения делает
агент. Пункты требуют HTTP(S) URL без userinfo; источники: github/jira/google_calendar,
классы: blocker/people/deadline/information. После успешной доставки агент подтверждает
sent; неудачная попытка получает failed, sent нельзя понизить. Отправленный бриф
получает sent_at один раз; read/click/positive/negative/reply устанавливают read_at
первым сигналом. Неизвестный item_id отклоняется; событие draft/failed — 409.

Вопрос нельзя читать всем участникам команды: только автору и адресату. Адресат —
существующий участник той же команды, без ограничения ролью, чтобы поддержать
ответственного из карточки. Первый сохранённый ответ неизменяемый; его точный повтор
разрешён. Содержимое FAQ и автор копируются из ответа в БД, из запроса их взять нельзя.
На вопрос публикуется одна запись FAQ. Доставка эскалаций через Telegram — задача агента.

`source_path` карточки содержит фиксированную версию и якорь раздела; FAQ — стабильный
ID записи. Эти служебные пути защищены авторизацией. Агент разрешает их относительно
BACKEND_URL для получения данных; пользовательские ссылки Telegram на источники
потребуют его обработчика с проверкой пользователя. Их нельзя выдавать за уже
доступные публичные ссылки. Редирект `/r/`, календарная база сравнения, /stats,
Telegram-интерфейс загрузки карточек и применение флагов в планировщике — зона агента.

## Этап 3: карточки, эскалации и настройки команды

`POST /api/v1/team-card` принимает тело YAML (до 1 МиБ, один документ),
рекомендуемый `Content-Type: application/yaml`. Требуются оба заголовка авторизации.
Наставник и тимлид загружают только свою команду; стажёр получает 403.
Формат соответствует `seed/team_cards/demo-orders.yaml`:

| Раздел | Поля |
|---|---|
| Корень | Обязательные `synthetic: true`, `team_id`, `name`; необязательные `notice`, `source_url`, `people`, `routing`, `do_not_disturb`, `tools`, `links`, `faq` |
| `people[]` | Обязательные `user_id`, `name`, `role` (название должности), `areas` (массив строк), `contact_url`; необязательный boolean `first_contact` |
| `routing[]` | Обязательные `situation`, `go_to`, `owner_id`, `wait_minutes` (целое 0–10080), `then_id`, `source_url` |
| `do_not_disturb[]` | Обязательные `person_id`, `direct_allowed` (boolean), `reason`, `via_id` |
| `tools[]` | Непустые строки |
| `links[]` | Обязательные `service`, `url` |
| `faq` | Только `[]`; публикация ответов — через отдельный REST с согласием автора |

Неизвестные поля и повторяющиеся `people.user_id` отклоняются. Все идентификаторы
участников должны существовать в своей команде; ссылки — HTTP(S), без userinfo
и пробельных символов. Массивы ограничены 100 элементами; обычные текстовые поля —
2000 байт, элементы строковых массивов — 200 байт, URL — 2048 байт.
Невалидная карточка возвращает 400 без новой версии:
`{"error":{"code":"validation_error","message":"Карточка не прошла проверку","fields":[{"field":"people[2].role","message":"обязательное поле"}]}}`.
Неизвестный ключ обозначается `*`, чтобы не отражать произвольные значения из YAML.
Синтаксическая ошибка имеет путь `document`. Ошибки не содержат исходные значения.

Изменение создаёт версию; повтор текущего содержимого возвращает прежнюю версию.
Конкурентные загрузки и seed сериализованы. Чтение по `version` сохраняет прежний
`source_path`; пути карточек и FAQ служебные, агент открывает их после авторизации.
Минимальные seed-файлы Этапа 2 по-прежнему импортируются; строгая полная схема
применяется к пользовательской загрузке через REST.

`GET /api/v1/flags` возвращает три boolean: `access_monitoring`, `team_escalation`,
`faq_publication`. Все по умолчанию true, env `FEATURE_ACCESS_MONITORING`,
`FEATURE_TEAM_ESCALATION`, `FEATURE_FAQ_PUBLICATION` изменяют значения по умолчанию.
БД имеет приоритет; некорректный boolean в env запрещает запуск.
Только тимлид меняет настройки своей команды:
`PUT /api/v1/flags/{name}` с `{"enabled":false}`. Изменения применяются без рестарта.
Все участники читают только свои настройки. Неизвестный флаг — 400.
Отключение `team_escalation` запрещает создание назначенных вопросов, отключение
`faq_publication` запрещает публикацию FAQ. Чтение, ответы на уже созданные вопросы
и оценки остаются доступными. `access_monitoring` читает агент перед фоновыми
проверками; ручные проверки и запись снимков разрешены.

`POST /api/v1/questions` дополнительно принимает
`"context":{"current_task":"ORD-118","checked_sources":["team-card:people","faq"]}`.
Задача ограничена 500 байтами, список — 20 непустыми строками до 500 байт.
Команда и неделя стажировки фиксируются backend из БД при создании; неизвестная
неделя — null. Повтор сохраняет исходную неделю; иной контекст с тем же ID — 409.
Подмена серверных полей запрещена. Вопрос и его контекст читают только автор и
назначенный участник своей команды. Доставку и повтор сообщений выполняет агент;
этот API не обещает гарантированную очередь доставки Telegram.

После ответа бота можно продолжить тот же вопрос:
`POST /api/v1/questions/{id}/escalate` с `{"assigned_to":"demo-anna"}`.
Назначает только автор вопроса и только участнику своей команды. Ответ бота,
контекст и оценки сохраняются. Повтор тому же участнику допустим, попытка
переназначить другому — 409. При отключённом team_escalation операция запрещена;
назначенный участник всё ещё может ответить. Повтор исходного POST questions
после назначения возвращает тот же вопрос и не сбрасывает назначение.

Ответ бота сохраняется автором вопроса через
`POST /api/v1/questions/{id}/bot-answer` с `{"text":"...","sources":["/api/v1/team-card?version=1#people"]}`.
Требуется непустой текст до 8000 байт и 1–20 источников: HTTP(S) или существующие
служебные пути карточки/FAQ своей команды. Содержательную достоверность внешних
ссылок проверяет агент по полученным данным. Сохранённый ответ неизменяемый,
точный повтор допустим; запись после ответа человека отклоняется.
`PATCH /api/v1/questions/{id}/bot-answer` с `{"helpful":true}` сохраняет `bot_helpful`.
Прежние `/answer` и `PATCH /questions/{id}` сохраняют ответ человека и `helpful`.
Эти оценки независимы. FAQ берёт исключительно ответ человека и его авторство.

`interns_list` и `GET /api/v1/interns` дополнительно возвращают `marks` с исходными
`requested_at`. Отсутствующий снимок — null, отсутствие отметок — `[]`.
Снимок содержит исходные статусы и отдельное поле `error`: ошибка источника
не означает `missing`. Подсчёт X/5 и текст числа дней выполняет агент по этим данным.

### Seed команды

`backend seed` одной транзакцией загружает пользователей и существующие файлы
`seed/team_cards/demo-orders.yaml`, `seed/access_catalog.yaml`. Если документы
не изменились, версия карточки не создаётся; смена A → B → A создаёт новую версию.
Ранее опубликованный FAQ, отметки, снимки и Telegram-привязки сохраняются.
Каталог обновляется по ID; отсутствующие в повторном файле объекты не удаляются.

`SEED_USERS_PATH`, `SEED_TEAM_CARD_PATH`, `SEED_ACCESS_CATALOG_PATH` задают пути
при запуске вне Compose. Если необязательные соседние файлы отсутствуют, загружаются
только пользователи; явно заданный отсутствующий путь — ошибка. У карточки обязательны
`synthetic: true`, team_id, name; people — список со ссылками на пользователей своей
команды. Это минимальная валидация seed; полная схема загрузки /teamcard — Этап 3.
FAQ публикуется через REST с согласием автора; в текущей seed-карточке `faq: []`.

Объект каталога:

```yaml
id: demo-repo
instrument: github # github | jira | miro | google_calendar | telegram
name: Учебный репозиторий
url: https://example.org/demo/repo
request_url: https://example.org/demo/request
owner_id: demo-oleg
roles: [intern, mentor, teamlead]
forbidden: false
```

Для forbidden=true нужен reason; request_url тогда необязателен.
У владельца и объекта одна команда. Заголовок каталога сохраняет поля текущего seed:
synthetic, notice, team_id, instruments, objects. Пустые объекты допустимы.
Дополнительно пользователь seed может иметь `logins: {github: synthetic-login}` и
`internship_started_on: '2026-11-01'`. Допустимые ключи логинов: github/jira/miro/google/telegram.
Отсутствие этих полей в повторном seed сохраняет известные значения; `logins: {}` их очищает.
Данные из репозитория не подменяются выдуманными аккаунтами или наполнением каталога.

### Приёмка MCP

```text
make up
make seed
make buddy-check
```

Последняя команда выполняет MCP Python SDK прямо из контейнера agent: реальный
backend, проверка ровно шести инструментов, чтение карточки demo-orders и проверка
отказа interns_list стажёру. Корпоративные MCP, аккаунты, Telegram и LLM не используются.
CI запускает эту проверку после seed. Все новые Go-инструменты также проверяются
Go SDK-клиентом, включая смену пользователя/роли в одной сессии, неверные аргументы
и безопасные ошибки. PostgreSQL-тесты покрывают атомарность seed, повторы и изоляцию.

## Этап 4: H0/H3, состояние и метрики

Согласованные решения и проверки сохраняются в `plans/ilya-backend-infra.md`.
Техническая дельта: `openspec/changes/stage-four-backend`; основные спецификации
не менялись и изменение ещё не архивировано.

- `POST /api/v1/briefs` сохраняет draft и возвращает `redirect_tokens`: отображение
  стабильного ID изменения в случайный 256-битный токен конкретного пункта/брифа/пользователя.
  Повтор того же содержимого возвращает прежние токены. Стабильные ID изменений нужны
  для дедупликации и не используются как публичные токены.
- `PATCH /api/v1/briefs/{id}` принимает `{ "status": "sent", "calendar": { ... } }`.
  Снимок (до 512 KiB) и доставка фиксируются одним UPDATE. `sent_at` берётся из БД.
  Повтор sent не меняет первоначальный снимок и время; sent нельзя понизить до failed.
  Ошибка отправки/источника и отсутствие снимка сохраняют предыдущую календарную базу.
  База выбирается из последней успешной доставки с непустым снимком; `{}` — успешный
  пустой календарь, `null`/отсутствие — источник не получен.
- `GET /api/v1/brief-state` возвращает `{last_sent, seen, calendar}`. ID уже доставленных
  изменений не теряются при рестарте. Failed/draft не участвуют в базе и дедупликации.
- `GET /api/v1/brief-settings` возвращает `{time: null, quiet: false}` по умолчанию.
  PATCH принимает непустое подмножество `time` (`HH:MM` либо `""` для сброса) и `quiet`
  (bool). Настройки только свои, время интерпретирует агент в `BRIEF_TIMEZONE`.
- `GET /api/v1/brief-stats` возвращает `{items: [{user_id, display_name, sent, read,
  clicked, positive, negative}]}`. Стажёр видит себя; наставник — своих стажёров;
  тимлид — стажёров команды. Все счётчики только по sent, один бриф не считается дважды
  в одном счётчике. Один бриф может иметь и positive, и negative: это счётчики сигналов
  оценки брифа, а не последняя оценка ответа H2/H3.
- Публичные `GET /r/{token}` без заголовков авторизации ведут только на сохранённый
  HTTP(S) URL: token является секретом ссылки. Черновики/failed/неизвестный токен — 404.
  Параметр `url` не используется. Click идемпотентен, первое `read_at` неизменно.
  `HEAD` не фиксирует чтение. Ответы: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`.
  Автоматический GET-просмотр ссылки также может считаться кликом; это сигнал открытия,
  не доказательство чтения человеком. Токены не выводятся в прикладной журнал backend.

`REDIRECT_BASE_URL` должен указывать на backend, доступный с телефона пользователя
(например, адрес машины в локальной сети при соответствующей настройке публикации порта).
По умолчанию Compose публикует backend только на loopback; развёртывание в интернете
и HTTPS в это поручение не входят. Агент использует только выданные backend токены.
Если токена нет, в том числе в полностью офлайн SeedData, остаётся прямая ссылка.

`BackendData` теперь читает состояние через REST, не дублирует его в памяти.
Кнопки ранее сохранённого брифа восстанавливают данные по ID после рестарта.
Соответствие Telegram message_id ↔ brief_id и список активных чатов планировщика пока
в памяти агента: ответ текстом на старое сообщение после полного рестарта этим этапом
не гарантируется. Офлайн-демо SeedData сохраняет прежнюю сессионную модель.

### Каталог и H3

В `access_catalog` поддерживается необязательное `target` без credentials:
`github`: owner/repo/org/team_slug; `jira`: project_key; `miro`: board_id;
`google_calendar`: calendarId/timeMin/timeMax; `telegram`: целый ненулевой chat_id.
Для всех разрешён keywords (до 20 строк). Неизвестные поля отклоняются с seed целиком.
Targets берутся из каталога авторизованного пользователя; общего кэша между командами нет.
Отсутствие реальных объектов остаётся допустимым в согласованной фикстурной приёмке.

Миграция 00005 создаёт совместимую с прежним агентом `rag_chunks` с `vector(384)`
для `intfloat/multilingual-e5-small`, сохраняя существующие строки. Индексация больше
не создаёт таблицу: сначала нужен старт backend/миграция. BM25 не требует БД/модели.
Модель и размерность другого индекса требуют отдельного согласования миграции.

### Журнал MCP и Grafana

`POST /api/v1/mcp-calls`: `{id, case, server, tool, outcome}`. Пользователь из авторизации,
время серверное; повтор id+содержимое безопасен, изменение — 409. Аргументы, ответы,
произвольный user_id и неизвестные поля не принимаются. Hub отправляет метаданные
успеха, ошибок и `tool_denied`; собственные SDK-чтения группируются как `buddy_read`.
При ошибке сохранения журналирования агент пишет безопасное предупреждение и продолжает
ответ пользователю. Гарантированная доставка аудита при падении БД не реализована.

Новые вопросы принимают `capability: h2|h3` (по умолчанию h2); H3 передаёт h3 явно.
Категория неизменна. Старые записи помечены unknown, их категория не угадывается.
H2/H3-метрики используют последнюю `bot_helpful`/`helpful` отдельно для бота/человека.

При `GRAFANA_DB_PASSWORD` backend подготавливает отдельный SQL login `buddy_metrics`:
SELECT только четырёх агрегатных views, без исходных таблиц и персональных текстов,
read-only по умолчанию и timeout 5 секунд. В Compose подготовка включена; вне Compose
можно не задавать переменную и подготовить роль администратором отдельно.
Просмотр Grafana: login `viewer`, пароль из `GRAFANA_VIEWER_PASSWORD` (локальный
fallback `buddy_viewer_local_demo`). `make up`/`make demo` подготавливают Viewer через
HTTP API; для уже запущенного стека — `make grafana-setup`. Admin `buddy` остаётся
для обслуживания; настройка пароля существующего admin в persisted volume остаётся
ответственностью владельца. API: https://grafana.com/docs/grafana/latest/developer-resources/api-reference/http-api/api-legacy/admin/.

Дашборд `/d/ai-buddy` показывает долю прочитанных/с переходами среди sent стажёрам,
последние оценки H2/H3, часы от requested_at до первого granted без ошибки, метаданные
MCP и отдельно отклонённые попытки. Пустая выборка доли/среднего — NULL.
Это данные разработки, не результаты пилота. Офлайн SeedData не наполняет PostgreSQL
и дашборд: для проверки хранения нужен синтетический REST-прогон или BackendData.

Проверка после `make seed`: `make stage4-check`. Она создаёт новые синтетические
брифы, вопросы и записи журнала в БД; запускайте её в проверочном Compose-проекте.
В CI эта проверка обязательна. Показатели Grafana — за всё время хранения.

## Живой GitHub вместо синтетического target

`GITHUB_REPOSITORY=owner/repo`, `GITHUB_TEAM_ID`, `GITHUB_CATALOG_OBJECT_ID` и
`GITHUB_USER_LOGINS` (JSON внутренних ID → GitHub login) задают конфигурацию чтения
на старте. Только выбранная команда получает live URL/target разрешённого GitHub-объекта
и свой login. Синтетические значения и запреты в БД сохраняются, повтор seed ничего
не сбрасывает. Отсутствующий mapped login не заменяется seed-логином. Невалидные значения
отклоняются безопасно. Все остальные поля профиля/каталога и REST-контракты сохранены.
Настройка проекта и токена: [mcp/GITHUB_PROJECT.md](../mcp/GITHUB_PROJECT.md).
