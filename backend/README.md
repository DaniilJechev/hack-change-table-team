# Backend · Этап 1

Go 1.24, net/http, pgx v5 через database/sql, миграции goose. При запуске применяются
встроенные SQL-миграции; ошибка БД/миграции останавливает процесс без вывода DSN.
`GET /health` сохраняет контракт Этапа 0. `GET /ready` проверяет БД.

## Локальные пользователи и приглашения

```text
make up
make seed
make invite USER_ID=demo-daniil TTL=24h
```

Seed берётся из существующего `seed/users.yaml`. Импорт повторяемый, атомарный,
не сбрасывает привязки и коды. Перенос существующего пользователя в другую команду
запрещён; изменение требует отдельной миграции. Роли: intern, mentor, teamlead.
Перед фиксацией проверяются все сохранённые связи с наставниками. Частичный seed
не может сменить роль наставника, если на него ещё ссылаются пользователи;
такой импорт откатывается целиком. Если связи сняты тем же импортом, смена роли разрешена.
Приглашение выдаётся только непривязанному пользователю, действует 24 часа по
умолчанию (не более 7 суток). Команда выводит код один раз; передать его сотруднику
для `/start <код>`, не записывать в репозиторий или журналы.

## REST для Эмиля

Машиночитаемая схема — [openapi.yaml](openapi.yaml).

`BACKEND_URL` и `BUDDY_SERVICE_KEY` уже переданы агенту через Compose.
Каждый `/api/v1/*` требует заголовок `X-Buddy-Key: <BUDDY_SERVICE_KEY>`.
В локальном Compose ключ по умолчанию демонстрационный `buddy_local_demo`;
для реального использования задать собственный ключ в `.env`. Пустой ключ при
запуске бинарника запрещён. REST доступен на host только через loopback.

| Запрос | Тело / ответ |
|---|---|
| `POST /api/v1/auth/bind` | `{"code":"…","telegram_user_id":123,"telegram_chat_id":123}` |
| `GET /api/v1/auth/telegram/123` | Профиль привязанного пользователя |

Успешный ответ: `{"user_id":"demo-daniil","display_name":"Даниил","role":"intern","team_id":"demo-orders","mentor_id":"demo-anna"}`.
Роль, команда и наставник берутся только из БД. Привязка разрешена только в личном
чате (положительные и одинаковые Telegram user/chat ID); повторный код не работает.
Коды хранятся как SHA-256; транзакция и блокировки защищают от одновременного
погашения. Конфликт не меняет прежнюю привязку и не расходует приглашение.

Ошибки имеют вид `{"error":{"code":"invalid_invitation","message":"Код не подошёл, спроси наставника"}}`:

| HTTP | code | Причина |
|---|---|---|
| 400 | invalid_request | Некорректный JSON, неизвестные поля, тело >4 KiB, не личный чат |
| 400 | invalid_invitation | Код неизвестен, истёк или уже использован |
| 401 | unauthorized | Неверный служебный ключ |
| 404 | not_found | Telegram ID не привязан |
| 409 | binding_conflict | Telegram/сотрудник уже связан |
| 503 | unavailable | БД недоступна |

В Telegram-обработчике `/start` Эмилю нужно передавать ID из `message.from_user.id`
и `message.chat.id`, а не из текста пользователя. Сам Telegram-обработчик этим
этапом части Ильи не изменён; `/start <код>` в боте ещё требует подключения REST.
MCP и прикладные данные H0–H3 появятся на следующих этапах.

## Проверки

`make test` и `make cover` запускают Go-тесты с отдельным временным PostgreSQL
в Docker. Если задан `TEST_DATABASE_URL`, используется эта БД с отдельными схемами
для каждого теста; таблицы разработчика не затрагиваются. CI задаёт отдельный
PostgreSQL service. `GO_RACE=1 make cover` включает race detector.
`make test-backend-integration` — только Go и PostgreSQL.

Запуск вне Docker: переменные `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`,
`PGPASSWORD`, `PGSSLMODE` или `DATABASE_URL`, плюс `BUDDY_SERVICE_KEY`.
`SEED_USERS_PATH` задаёт путь seed для `backend seed` (в Compose `/seed/users.yaml`).
