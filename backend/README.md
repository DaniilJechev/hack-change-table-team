# Backend · Этапы 1–2

Go 1.24, net/http, pgx v5 через database/sql, миграции goose. При запуске применяются
встроенные SQL-миграции; ошибка БД/миграции останавливает процесс без вывода DSN.
`GET /health` сохраняет контракт Этапа 0. `GET /ready` проверяет БД.

## Локальные пользователи и приглашения

```text
make up
make seed
make invite USER_ID=demo-daniil TTL=24h
```

Seed берётся из существующего `seed/users.yaml`. Импорт повторяемый, атомарный,
не сбрасывает привязки и коды. Перенос существующего пользователя в другую команду
запрещён; изменение требует отдельной миграции. Роли: intern, mentor, teamlead.
Перед фиксацией проверяются все сохранённые связи с наставниками. Частичный seed
не может сменить роль наставника, если на него ещё ссылаются пользователи;
такой импорт откатывается целиком. Если связи сняты тем же импортом, смена роли разрешена.
Приглашение выдаётся только непривязанному пользователю, действует 24 часа по
умолчанию (не более 7 суток). Команда выводит код один раз; передать его сотруднику
для `/start <код>`, не записывать в репозиторий или журналы.

## REST для Эмиля

Машиночитаемая схема — [openapi.yaml](openapi.yaml).

`BACKEND_URL` и `BUDDY_SERVICE_KEY` уже переданы агенту через Compose.
Каждый `/api/v1/*` требует заголовок `X-Buddy-Key: <BUDDY_SERVICE_KEY>`.
В локальном Compose ключ по умолчанию демонстрационный `buddy_local_demo`;
для реального использования задать собственный ключ в `.env`. Пустой ключ при
запуске бинарника запрещён. REST доступен на host только через loopback.

| Запрос | Тело / ответ |
|---|---|
| `POST /api/v1/auth/bind` | `{"code":"…","telegram_user_id":123,"telegram_chat_id":123}` |
| `GET /api/v1/auth/telegram/123` | Профиль привязанного пользователя |

Успешный ответ: `{"user_id":"demo-daniil","display_name":"Даниил","role":"intern","team_id":"demo-orders","mentor_id":"demo-anna"}`.
Роль, команда и наставник берутся только из БД. Привязка разрешена только в личном
чате (положительные и одинаковые Telegram user/chat ID); повторный код не работает.
Коды хранятся как SHA-256; транзакция и блокировки защищают от одновременного
погашения. Конфликт не меняет прежнюю привязку и не расходует приглашение.

Ошибки имеют вид `{"error":{"code":"invalid_invitation","message":"Код не подошёл, спроси наставника"}}`:

| HTTP | code | Причина |
|---|---|---|
| 400 | invalid_request | Некорректный JSON, неизвестные поля, тело >4 KiB, не личный чат |
| 400 | invalid_invitation | Код неизвестен, истёк или уже использован |
| 401 | unauthorized | Неверный служебный ключ |
| 404 | not_found | Telegram ID не привязан |
| 409 | binding_conflict | Telegram/сотрудник уже связан |
| 503 | unavailable | БД недоступна |

Telegram-обработчик `/start` уже подключён к REST в main: ID берутся из
`message.from_user.id` и `message.chat.id`, а профиль — из ответа backend.
Прикладные маршруты и MCP Этапа 2 описаны ниже.

## Проверки

`make test` и `make cover` запускают Go-тесты с отдельным временным PostgreSQL
в Docker. Если задан `TEST_DATABASE_URL`, используется эта БД с отдельными схемами
для каждого теста; таблицы разработчика не затрагиваются. CI задаёт отдельный
PostgreSQL service. `GO_RACE=1 make cover` включает race detector.
`make test-backend-integration` — только Go и PostgreSQL.

Запуск вне Docker: переменные `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`,
`PGPASSWORD`, `PGSSLMODE` или `DATABASE_URL`, плюс `BUDDY_SERVICE_KEY`.
`SEED_USERS_PATH` задаёт путь seed для `backend seed` (в Compose `/seed/users.yaml`).

## Этап 2: buddy-mcp и наши данные

`/mcp` — настоящий Streamable HTTP на [официальном MCP Go SDK](https://github.com/modelcontextprotocol/go-sdk),
закреплённом на v1.3.1 для совместимости с Go 1.24. JSON-ответы, stateless transport:
сервер не сохраняет права пользователя в MCP-сессии. `initialize`, `tools/list` и каждый
`tools/call` требуют **оба** заголовка `X-Buddy-Key` и `X-Buddy-User`.
Профиль, роль и команда перечитываются из PostgreSQL на каждом HTTP-запросе;
роль и team_id в аргументах инструментов не принимаются. Таймаут запроса — 5 секунд,
максимальное тело — 1 MiB. Ошибки БД/секреты не передаются клиенту.

| MCP-инструмент | Аргументы | Результат |
|---|---|---|
| `user_profile_get` | `{}` | Свой профиль, `teamlead_id`, `logins`, `internship_week` |
| `team_card_get` | `{"section":"people"}` или `{}` | `team_id`, `version`, `document`, `source_path` |
| `team_faq_search` | `{"text":"Kafka"}` | `items`: до 20 опубликованных ответов своей команды |
| `access_catalog_get` | `{"objects":["repo"]}` или `{}` | `items`: объекты своей команды для своей роли |
| `access_marks_get` | `{}` | `items`: свои `object_id`, `requested_at` |
| `interns_list` | `{}` | `items`: профили стажёров и `snapshot` (либо null) |

Все инструменты имеют `readOnlyHint=true`. `interns_list` доступен наставнику
(только его стажёры) и тимлиду (стажёры своей команды). Неизвестные аргументы,
включая чужую команду или пользователя, отклоняются схемой SDK.
Неизвестный пользователь/неверный ключ — HTTP 401; ошибка внутри инструмента — MCP
`isError=true` с безопасным русским текстом. При отсутствии карточки — «Данные не найдены».
Пустые наборы возвращаются как `items: []`. Неделя стажировки — null, если дата неизвестна;
фиктивные логины и даты не подставляются.

### REST-контракты

Все новые маршруты требуют те же два заголовка. Поля пользователя, команды,
автора ответа и серверного времени вычисляются сервером; лишние поля отклоняются.
Существующие `/api/v1/auth/*` по-прежнему требуют только служебный ключ.
Точные схемы запросов и ответов — [openapi.yaml](openapi.yaml).

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/profile` | Свой расширенный профиль |
| `GET /api/v1/team-card?section=people&version=1` | Своя карточка, необязательные раздел и версия |
| `GET /api/v1/access-catalog?object=repo` | Каталог; `object` можно повторить |
| `PUT /api/v1/access-marks/{object}` | «Я запросил», **пустое тело** |
| `GET /api/v1/access-marks` | Свои отметки |
| `POST /api/v1/access-snapshots` | `{"id":"s1","objects":[{"object_id":"repo","status":"missing"}]}` |
| `GET /api/v1/access-snapshots/latest` | Последний свой снимок |
| `GET /api/v1/interns` | Те же права и данные, что у `interns_list` |
| `POST /api/v1/briefs` | `{"id":"b1","items":[]}` — новый draft |
| `GET /api/v1/briefs/{id}` | Свой бриф |
| `PATCH /api/v1/briefs/{id}` | `{"status":"sent"}` или `{"status":"failed"}` |
| `POST /api/v1/briefs/{id}/events` | `{"id":"e1","kind":"read"}`; click требует `item_id` |
| `POST /api/v1/questions` | `{"id":"q1","text":"Зачем Kafka?","assigned_to":"demo-anna"}` |
| `GET /api/v1/questions/{id}` | Доступен создателю вопроса и назначенному адресату |
| `POST /api/v1/questions/{id}/answer` | `{"text":"Ответ человека"}`, только назначенный адресат |
| `PATCH /api/v1/questions/{id}` | `{"helpful":true}`, только создатель вопроса с ответом |
| `POST /api/v1/faq` | `{"id":"f1","question_id":"q1","consent":true}`, только автор ответа |
| `GET /api/v1/faq/{id}` | Опубликованный FAQ своей команды |
| `GET /api/v1/faq?text=Kafka` | Буквальная подстрока в вопросе или ответе, без LLM |

ID записей задаёт агент: 1–128 ASCII-символов, первый буквенно-цифровой, далее
буквы/цифры и `._:-`. Повтор с тем же ID и содержимым возвращает прежнюю запись;
другое содержимое — 409 `conflict`. `PUT access-marks` возвращает первоначальную дату;
отметить неизвестный, скрытый для роли или запрещённый объект нельзя (404).
В снимке принимаются только объекты своей команды/роли без повторов. Поле `error`
предназначено для короткого безопасного кода ошибки проверки, до 256 байт;
агент должен сохранять предыдущий известный статус при недоступном инструменте.
Последний снимок определяется порядком вставки, повтор старого ID его не меняет.

Бриф хранит все нормализованные пункты (до 100); выбор пяти для сообщения делает
агент. Пункты требуют HTTP(S) URL без userinfo; источники: github/jira/google_calendar,
классы: blocker/people/deadline/information. После успешной доставки агент подтверждает
sent; неудачная попытка получает failed, sent нельзя понизить. Отправленный бриф
получает sent_at один раз; read/click/positive/negative/reply устанавливают read_at
первым сигналом. Неизвестный item_id отклоняется; событие draft/failed — 409.

Вопрос нельзя читать всем участникам команды: только автору и адресату. Адресат —
существующий участник той же команды, без ограничения ролью, чтобы поддержать
ответственного из карточки. Первый сохранённый ответ неизменяемый; его точный повтор
разрешён. Содержимое FAQ и автор копируются из ответа в БД, из запроса их взять нельзя.
На вопрос публикуется одна запись FAQ. Доставка эскалаций через Telegram — задача агента.

`source_path` карточки содержит фиксированную версию и якорь раздела; FAQ — стабильный
ID записи. Эти служебные пути защищены авторизацией. Агент разрешает их относительно
BACKEND_URL для получения данных; пользовательские ссылки Telegram на источники
потребуют его обработчика с проверкой пользователя. Их нельзя выдавать за уже
доступные публичные ссылки. Редирект `/r/`, календарная база сравнения, /stats,
feature flags и загрузка карточек через Telegram относятся к следующим этапам.

### Seed команды

`backend seed` одной транзакцией загружает пользователей и существующие файлы
`seed/team_cards/demo-orders.yaml`, `seed/access_catalog.yaml`. Если документы
не изменились, версия карточки не создаётся; смена A → B → A создаёт новую версию.
Ранее опубликованный FAQ, отметки, снимки и Telegram-привязки сохраняются.
Каталог обновляется по ID; отсутствующие в повторном файле объекты не удаляются.

`SEED_USERS_PATH`, `SEED_TEAM_CARD_PATH`, `SEED_ACCESS_CATALOG_PATH` задают пути
при запуске вне Compose. Если необязательные соседние файлы отсутствуют, загружаются
только пользователи; явно заданный отсутствующий путь — ошибка. У карточки обязательны
`synthetic: true`, team_id, name; people — список со ссылками на пользователей своей
команды. Это минимальная валидация seed; полная схема загрузки /teamcard — Этап 3.
FAQ публикуется через REST с согласием автора; в текущей seed-карточке `faq: []`.

Объект каталога:

```yaml
id: demo-repo
instrument: github # github | jira | miro | google_calendar | telegram
name: Учебный репозиторий
url: https://example.org/demo/repo
request_url: https://example.org/demo/request
owner_id: demo-oleg
roles: [intern, mentor, teamlead]
forbidden: false
```

Для forbidden=true нужен reason; request_url тогда необязателен.
У владельца и объекта одна команда. Заголовок каталога сохраняет поля текущего seed:
synthetic, notice, team_id, instruments, objects. Пустые объекты допустимы.
Дополнительно пользователь seed может иметь `logins: {github: synthetic-login}` и
`internship_started_on: '2026-11-01'`. Допустимые ключи логинов: github/jira/miro/google/telegram.
Отсутствие этих полей в повторном seed сохраняет известные значения; `logins: {}` их очищает.
Данные из репозитория не подменяются выдуманными аккаунтами или наполнением каталога.

### Приёмка MCP

```text
make up
make seed
make buddy-check
```

Последняя команда выполняет MCP Python SDK прямо из контейнера agent: реальный
backend, проверка ровно шести инструментов, чтение карточки demo-orders и проверка
отказа interns_list стажёру. Корпоративные MCP, аккаунты, Telegram и LLM не используются.
CI запускает эту проверку после seed. Все новые Go-инструменты также проверяются
Go SDK-клиентом, включая смену пользователя/роли в одной сессии, неверные аргументы
и безопасные ошибки. PostgreSQL-тесты покрывают атомарность seed, повторы и изоляцию.
