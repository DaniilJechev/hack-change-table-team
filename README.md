Telegram-помощник для стажёров. Кейс Hack&Change 2026. Реализованы Этапы 0–4:
Router и Executors, H0 (бриф), H1 (доступы), H2 (вопросы о команде), H3 (playbook),
REST-привязка Telegram, buddy-mcp, постоянные данные backend и метрики Grafana.
Приёмка — на синтетических фикстурах, без настоящей LLM и внешних аккаунтов.
Текущий статус и ограничения — [отчёт об интеграции](reports/MAIN_INTEGRATION_REPORT.md).
Синтетические карточки не являются регламентами Авито.

## Запуск

Нужны Docker Engine с Compose v2, GNU Make и Python 3.12 на хосте:
`make up` вызывает Python-скрипт настройки Grafana Viewer. Go на хосте для запуска не нужен.

```sh
make up
```

На Windows без Make эквивалентный запуск и настройка Viewer:

```powershell
docker compose up --build -d --wait --wait-timeout 180
python infra/setup_grafana.py
```

Пять сервисов: PostgreSQL 16 + pgvector, Redis 7, Grafana, Go backend и Python agent.
Порты доступны только локально: backend 8080, agent 8081, Grafana 3000.
Проверки: `http://localhost:8080/health`, `http://localhost:8081/health`, `http://localhost:3000/api/health`.
Grafana: для просмотра пользователь `viewer`, локальный пароль `buddy_viewer_local_demo`
(переопределяется `GRAFANA_VIEWER_PASSWORD`). `make up` подготавливает Viewer;
для обслуживания сохранён admin `buddy` с `GRAFANA_ADMIN_PASSWORD` (fallback `buddy_local_demo`).

Без `.env` каркас работает offline, без Telegram и без внешних аккаунтов. В контейнере:

```sh
docker compose exec agent python -m buddy --smoke
```

Это проверка реального aiogram Dispatcher с фейковым транспортом и fake LLM. Полный сценарий H0–H3 в демо-режиме — `python scripts/demo_transcript.py`.
`make demo` использует `.env.example` и не требует аккаунтов (переменные shell имеют приоритет в Compose).

## Telegram и LLM

Скопируйте `.env.example` в `.env`, задайте `TELEGRAM_BOT_TOKEN` от @BotFather, перезапустите agent.
Не запускайте второй polling-процесс для того же токена. Бот отвечает на `/start` и `/help`.
Обработчик `/start <код>` привязывает Telegram через REST; повторный `/start` загружает
профиль. В личном чате доступны данные своей команды; без приглашения можно явно
включить синтетический `/demo`, если разрешён `DEMO_MODE`. Бот в текущем окружении
остановлен по указанию пользователя; его запуск требует отдельного поручения.

Для привязки к backend загрузите синтетические данные: `make seed`, затем
`make invite USER_ID=demo-daniil` и откройте полученное приглашение.
Контракт и примеры — [backend/README.md](backend/README.md), схема — [OpenAPI](backend/openapi.yaml).
Опциональные готовые MCP поднимаются через `make mcp-up`; конфигурация, ограничения
чтения и проверка `make mcp-list` — в [mcp/README.md](mcp/README.md).

Выбран адаптер **OpenRouter**, модель по умолчанию в Compose `openrouter/auto`.
Для live LLM задайте `DEMO_MODE=false`, `LLM_PROVIDER=openrouter`, `LLM_MODEL` и `LLM_API_KEY`.
Для другого совместимого API: `LLM_PROVIDER=compatible` и `LLM_BASE_URL=https://ваш-сервис/v1`.
Провайдер и модель читаются только из env. Секреты не коммитятся; `.env.example` содержит пустые секреты.
В демо всегда используется FakeLLM; тесты не тратят API-бюджет. Ошибка или таймаут <=20 секунд возвращают шаблон.
`/start` вообще не обращается к LLM. Модель эмбеддингов нужна только при `RAG_SEARCH_MODE=vector|rrf` (см. раздел про Этап 4).

## Тесты и покрытие

Нужны Python 3.12, Go >=1.24, uv 0.9.5 и Docker для интеграционных Go-тестов;
для OpenSpec Node >=22.12. Тесты создают отдельный временный PostgreSQL, а при
заданном `TEST_DATABASE_URL` используют в нём изолированные схемы.

```sh
make setup
make test
make cover
make validate
```

Без Make: `uv sync --project agent --frozen --extra dev --python 3.12`, затем `python scripts/check.py coverage`.
`uv.lock` фиксирует версии зависимостей. Python-тесты используют фейки и httpx MockTransport.
Порог покрытия строго >80% отдельно для backend и agent; в CI проверяются также lint, OpenSpec и Compose.
`make smoke` проверяет offline /start, здоровье пяти контейнеров, HTTP backend/agent/Grafana, PING Redis и SQL с типом vector. `SMOKE_ARGS=--demo` дополнительно проверяет DEMO_MODE.
`make ps`, `make logs` и `make check-config` показывают состояние, логи и проверяют конфигурацию.
`make down` останавливает сервисы, сохраняя тома с данными.
`make ingest` строит индекс playbook (см. H3 ниже). `make record-fixtures` пока остаётся
заглушкой; запись через MCP CLI `call --live --record` описана в [mcp/CLIENTS.md](mcp/CLIENTS.md).
PostgreSQL применяет init.sql только на новом томе; изменение пароля в .env не меняет пароль существующей БД.

## Структура и дальнейшая работа

- `backend/` — Go: миграции, REST, buddy-mcp, привязка, данные команды, брифы и редирект.
- `agent/buddy/` — Telegram-бот, Router, Executors H0–H3, MCP-клиенты, демо и планировщик.
- `infra/` — pgvector init и Grafana provisioning.
- `seed/` — синтетические пользователи двух команд, карточки и каталог доступов.
- `evals/survey.md` — готовая анкета для стажёров. Результаты пока не собраны.
- `mcp/` — конфигурация готовых серверов чтения и проверенный набор инструментов.
- `fixtures/` — три шага синтетического сценария; `data/playbook/` — снимок публичного playbook.
- `openspec/` — спецификации и изменения; `docs/` — продукт, архитектура, roadmap.

Корпоративные сервисы — только чтение. Tools/list проверяется с синтетическими
credentials; реальные вызовы требуют подготовки тестовых аккаунтов и клиентов агента.
Начните с AGENTS.md и трёх документов в docs/. Поведение сверяйте с openspec/specs/.

### Привязка Telegram (Этап 1)

После запуска backend выполните `make seed`, затем `make invite USER_ID=demo-daniil`.
Передайте выданный одноразовый код адресату приватно. В личном чате бот принимает
`/start <код>`, повторный `/start` загружает профиль из backend. Роль и команда
определяются сервером; групповые сообщения не активируют приглашение.
Для локального агента нужны `BACKEND_URL` и `BUDDY_SERVICE_KEY` в `.env`, в Compose
они уже передаются. Без этих настроек остаётся автономный каркас. H0–H3 ещё не включены.
При недоступности backend бот отвечает безопасным шаблоном без LLM.

`seed/check_stage_one.py` — приёмка свежего изолированного Compose-проекта
`buddy-stage1-acceptance`: настоящий REST/PostgreSQL, offline Telegram и discovery
официальных GitHub/Jira/Calendar MCP. Запускается и в CI; секреты и код не печатает.
Приёмка не вызывает корпоративные tools/call и требует свежей тестовой БД.


### Этап 2: Router и демо (Эмиль + Даниил)

Реализованы Router с 16 кейсами RT-01, правила без LLM, каркас Executors с белыми списками
и лимитом 3 вызова. На Этапе 2 это был каркас; бизнес-сценарии H0–H3 реализованы
на Этапах 3–4 и описаны ниже.

В личном чате:
- `/demo` — явно включить публичный синтетический пример без реальной привязки;
- `/demo next`, `/demo reset`, `/demo off` — следующий шаг, сброс и выход;
- `/ask` — восемь типов вопросов о команде; кнопки идут прямо в Executor;
- обычный текст после `/demo` или реальной привязки — маршрутизация запроса.

Демо изолировано по пользователям, теперь имеет три шага и не обращается к внешним сервисам.
В live-режиме `/demo` отключён. Без активного демо требуется настоящий профиль из backend.
Сессии демо не переживают перезапуск. Публичный synthetic-профиль не заменяет реальную привязку.

Проверка из корня:
```sh
uv run --project agent --frozen --extra dev python seed/build_stage_two.py
uv run --project agent --frozen --extra dev python evals/run_router.py
uv run --project agent --frozen --extra dev python evals/run_router.py --dataset evals/router/holdout.jsonl
uv run --project agent --frozen --extra dev pytest agent/tests --cov=buddy
```

Карточка команды и каталог синтетические; правила доступа в них не являются регламентами Авито.
Контракты и cross-reference проверяются в `buddy/demo/contracts.py`.
Данные и отчёты оценки — `evals/router/`; полный доклад — `reports/STAGE_2_EMIL_DANIIL_REPORT.md`.
Backend/buddy-mcp Ильи и бизнес-исполнители следующих этапов в это поручение не входят.


### Этап 3: H1 и H2 на синтетических фикстурах

Текущий функционал: `/access`, доступы под ORD-118, `[Где запросить]` / `[Я запросил]`,
перепроверка и уведомление об изменениях, черновик напоминания без отправки владельцу,
`/interns` наставника; Q1–Q8, ссылки на источники, «не нашёл», эскалация, ответ,
согласие на FAQ и оценки. Backend выполняет versioned YAML upload, флаги команды,
контекст/ответы/оценки вопросов и отдельное происхождение ответа бота/человека.

Сценарий без аккаунтов:
1. `/demo`, `/access`, кнопка «Я запросил» у Miro.
2. `/demo next` — в новом шаге доступ появился; приходит только уведомление об изменении.
3. `/ask`, «Кто отвечает за Kafka?», «Можно написать Петру напрямую?», «Где доска планирования?».
4. «Почему у нас Kafka, а не RabbitMQ?» → «Спросить» → «Ответить … (демо)» → написать ответ → сохранить в FAQ.
5. Повторить вопрос — ответ приходит из FAQ со ссылкой; оценить его.
6. `/demo mentor`, `/interns`; `/teamcard` и YAML-файл/текст своей команды (не более 1 МиБ).
7. `/demo intern` возвращает синтетического стажёра; `/demo reset` сбрасывает свою сессию, `/demo off` выходит.

Роли в демо — только предопределённые синтетические участники; реальная привязка не меняется.
В live-режиме эта смена ролей запрещена. Корпоративные сервисы только читаются; изменения
вносятся только в наши данные. Планировщик учитывает access_monitoring, эскалации —
team_escalation, публикация — faq_publication. Если сохранён снимок, база мониторинга
восстанавливается после пересоздания обработчика. После запуска реальные пользователи
вновь включаются в проверку при обращении к боту; демо намеренно сбрасывается при перезапуске.

Действующие ограничения: настоящие внешние API/OAuth и LLM не проверялись и не входят в
согласованную приёмку. Внешние targets поддерживаются backend Этапа 4; для живого окружения нужны их
реальные значения и постоянная адресная книга Telegram. Если адресат недоступен, бот сообщает об этом, а не обещает
несуществующую автоматическую доставку.

Проверки: `evals/README.md`. Полный доклад: `reports/STAGE_3_COMPLETION_REPORT.md`.
Ревью Ильи: `reports/PR_11_REVIEW_REPORT.md`. Живой контейнер бота остановлен по просьбе пользователя;
самостоятельно `make up` / `make demo` на его окружении не запускать.

### Этап 4: H0 (бриф) и H3 (playbook) на синтетических фикстурах

**H0.** `/brief` или «что нового?» собирает изменения из GitHub, Jira и Google Calendar с момента
последнего *доставленного* брифа: запрошенные изменения и ревью в PR, упоминания и новые задачи в
Jira, сроки, перенос, отмену и появление встреч (календарь сравнивается с сохранённым снимком).
Пункты ранжируются «блокер → запрос людей → дедлайн → информация», показываются первые 5, остальные —
под кнопкой «Ещё N». «▶ Главное сегодня» выбирает правило; LLM (если подключена) только
переформулирует строки по `item_id`, ссылки всегда подставляет код. Пункт без рабочей ссылки в бриф не
попадает. «Есть что по PR?» даёт только Git. Кнопки [✅ Прочитал] 👍 👎, открытие «Ещё N» и ответ на
сообщение брифа отмечают его прочитанным; `/stats` показывает долю прочитанных (цель ≥ 60 %).
`/settings brief 09:00` и `/settings quiet on|off` — время и тихий режим. В живом режиме бриф уходит
сам за 30 минут до первого стендапа (иначе в `BRIEF_TIME`), не в выходные и не в день отсутствия.

**H3.** Вопрос по процессам и культуре Авито бот ищет в снимке
[AvitoTech Playbook](https://github.com/avito-tech/playbook) (коммит `0c1d2aa`, 622 фрагмента по
заголовкам) и отвечает только по найденным фрагментам со ссылкой на файл и раздел на GitHub и
пометкой, что документ может быть устаревшим. Если ответа нет — «В playbook этого нет» и кнопка
[Спросить наставника]. Без LLM бот показывает сами фрагменты.

Режим поиска задаёт `RAG_SEARCH_MODE`:

| Значение | Как ищет | Что нужно |
|---|---|---|
| `bm25` (по умолчанию) | по словам, со стеммингом | ничего: модель не загружается, БД не нужна |
| `vector` | эмбеддинги `multilingual-e5-small` + pgvector | образ с `AGENT_EXTRAS="--extra rag"`, один раз `make ingest-compose` |
| `rrf` | объединение обоих списков (Reciprocal Rank Fusion) | то же |

В `vector` и `rrf` векторы фрагментов считаются один раз при индексации; при работе бота модель
загружается при первом вопросе по playbook и считает только вектор вопроса. Если модель или база
недоступны, поиск сам переходит на `bm25`. Локально без Docker: `make setup-rag`, задать
`RAG_SEARCH_MODE` и `RAG_DATABASE_URL`, затем `make ingest`. Замеры качества — в `evals/README.md`.

Демо теперь из трёх шагов: `/demo` → `/brief` → `/demo next` (появился доступ к Miro) → `/demo next`
(следующее утро, новый бриф). Полный протокол — `reports/STAGE_4_DEMO_TRANSCRIPT.md`
(`python scripts/demo_transcript.py`), сценарий видео — `reports/STAGE_4_VIDEO_SCRIPT.md`,
доклад — `reports/STAGE_4_EMIL_DANIIL_REPORT.md`.

Backend Этапа 4 сохраняет календарь, статистику и настройки брифа в PostgreSQL.
При `REDIRECT_BASE_URL`, доступном устройству пользователя, сохранённые пункты открываются
через случайные токены `/r/<token>` с учётом кликов; офлайн SeedData использует прямые ссылки.
Grafana `/d/ai-buddy` читает агрегаты через отдельную SQL-роль без доступа к исходным таблицам.
Контракты и ограничения — в [backend/README.md](backend/README.md).
Реальные аккаунты и реальная LLM не проверялись.
